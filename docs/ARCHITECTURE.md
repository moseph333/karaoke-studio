# Karaoke Studio: Architecture

This guide explains how Karaoke Studio is put together: the FastAPI backend and its processing pipelines, the background jobs that run on finished songs, the stem separation and lyric sync engines with their worker protocols, and the React frontend with its design system, studio layout and command palette.

## 2. Backend

### 2.1 Application entry point

`backend/main.py` builds the FastAPI app, installs the middleware (security headers, CORS, session authentication), mounts static media and the built frontend, includes the routers, and creates the shared service singletons (`separator`, `aligner`, `audio_mixer`, `lyrics_service`, `video_renderer`, …). Its `lifespan` marks the jobs the previous server process left running as interrupted before the first request (see Cancellation in §2.3) and deletes what the jobs it cut off left half-made: the videos and scratch mixes of renders (see Video in §2.8), the staged stems of re-separations (`reseparation.remove_staged_stems`, see §2.5) and the mixer's unfinished `*.tmp_*.wav` and `*.tmp_*.m4a` files (`master_audio.remove_unfinished_mixes`). It then starts a daemon thread that prunes every song's cached mixes once (`master_audio.prune_mixes_of_every_song`, see Master audio in §2.8), so the mixes past the limit on songs no one has remixed since go too, without delaying startup. A failure in any of these steps is logged and never stops startup or the other steps. `logging_setup.configure_logging()` gives the app's own loggers (`karaoke_backend` and `backend.*`) a timestamped stderr handler at INFO (`LOG_LEVEL`), since Uvicorn configures only its own. Its formatter escapes control characters in messages, so text from a request cannot forge log lines, and the outermost middleware (`middleware.RequestContext`) gives each request an id (a well-formed incoming `X-Request-ID`, else a new one) that tags every line logged while it is handled, including by the background jobs it starts, and comes back in the response's `X-Request-ID`. Tests monkeypatch these singletons, so services are always reached through `backend.main` at call time.

**Authentication.** When `APP_PASSWORD` is set, every `/api/*` request except `GET /api/health` and `/api/auth/*`, and every `/static/*` file, needs a session: an HMAC-signed token from `POST /api/auth/login` (also set as an `HttpOnly` cookie; signed with the passphrase keyed by the server's secret, `SESSION_SECRET` or else a random `<data dir>/.session_secret` created with mode 0600, so a leaked token cannot be used to test passphrase guesses offline), the `X-App-Password` header, or `Authorization: Bearer`. Without one, `GET /api/health` answers from the cached update status and ignores `check_remote`. Wrong passphrases are rate limited per client IP (`LOGIN_RATE_LIMIT_*`, HTTP 429 with `Retry-After`), whether they arrive at `POST /api/auth/login` or as credentials on any route (`auth.authenticate_request`, used by the middleware, `GET /api/auth/status` and `check_remote`). A wrong value or a token with the wrong signature counts once per window however often it is resent, and a request carrying several credentials has no more new values compared than the window has room for; a token signed with the passphrase but expired, a request with no credential and a valid passphrase sent beside a stale token count nothing. A client IP over the limit gets the 429 before its credentials are compared, on every protected route, so a right guess cannot get through; `/api/auth/status` answers `authenticated: false` instead, and `check_remote` is ignored. These handlers are async, so checking and counting a guess is one step on the event loop. A 401 for cookie credentials also expires both session cookies, so browsers stop resending a stale one. The client IP is the `X-Forwarded-For` entry `FORWARDED_TRUSTED_HOPS` places from the end (default 1: the one the nearest proxy wrote; 2 for cloudflared in front of Nginx Proxy Manager; 0 ignores the header), else the socket address. Keep the app port reachable only through those proxies; a client that connects directly can set the header itself. The same goes for every trusted proxy but the outermost: with 2, a client that reaches Nginx Proxy Manager without passing cloudflared picks its own key, so use 1 if Nginx Proxy Manager also serves clients directly. The CORS middleware sits outside the passphrase check (and inside the host check, body limit and security headers): a preflight from an allowed origin (`ALLOWED_ORIGINS`, plus any localhost port) is answered without credentials, which browsers never send with one, and a 401 carries the CORS headers so a studio served from that origin can read it and show the login.

**The owner.** The studio has no accounts, so the server's owner is told apart by a second secret, `ADMIN_PASSWORD` (`backend/admin_auth.py`). The `/api/admin/*` routes sit behind the studio passphrase like every other route and then ask for the admin one: `POST /api/admin/login` trades it for an admin token, signed like a session token but with a key of its own (the passphrase prefixed with `admin\0`, so a session token is never an admin token even where both passphrases are the same), which the page sends as `X-Admin-Token`; scripts may send the passphrase itself as `X-Admin-Password`. Only headers count, never a cookie, so no other website's request can carry it. A refusal is always 403, never 401: the studio takes a 401 from any route to mean its session ended (`apiFetch`) and would sign a singer out for mistyping the admin passphrase. Wrong admin passphrases use the login limit's counts and window but are counted under their own key (`admin|<ip>`), so guessing at the admin passphrase locks that address out of the admin routes only. With `ADMIN_PASSWORD` unset the routes refuse, `GET /api/auth/status` says `admin: false` and the studio offers no Server settings page.

**A show-only sign-in.** A show (§3.5) may be run by somebody who should not have the studio: a venue's host needs the queue, the songs and the karaoke videos, not the means to edit or delete anything. `SHOW_PASSWORD` is a third secret for them (`backend/show_auth.py`). `POST /api/auth/show-login` trades it for a show token, signed like a session token with a key of its own (`"show\0" + passphrase`, so it cannot pass as a session or an admin token, nor they as one), good for seven days; the host screen sends it in `X-Show-Token`, and the route also sets it as the `HttpOnly` cookie `show_token`, for the media a page loads by itself (the song's audio, a video's copy, cover art). `PassphraseAuth` looks for it only on a request that has no valid session: one a show makes goes through, anything else answers 403 with `SHOW_ONLY_DETAIL`, never 401, which the host screen would take for being signed out. What a show makes is `show_auth.ALLOWED`, matched on the method and the whole path: `GET /api/projects`, `GET /api/project/{id}` and its `/backdrop`, `GET /api/capabilities`, `POST /api/search`, the three `/api/show/videos` routes, `GET` and `POST /api/show/requests` (the request list is read and added to; removing from it is the studio's) and `GET /static/*`. A new route is therefore closed to a show token until it is listed there. Wrong show passphrases and forged show tokens are limited per address under their own key (`show|<ip>`). `GET /api/auth/status` says `show` (the server has a show passphrase and a studio one) and `show_authenticated`; changing or emptying `SHOW_PASSWORD` ends every show sign-in. The frontend keeps the token apart from the studio's (`api.ts`, `karaoke_show_token`): sent in the studio's headers it would count as a wrong studio passphrase.

**Static media.**

| Mount | Folder | Contents |
| :--- | :--- | :--- |
| `/static/downloads` | `downloads/` | original audio, cover art |
| `/static/stems` | `stems/<track>/` | `vocals.wav`, `instrumental.wav`, `separation.json` (how they were made), custom instrumentals |
| `/static/output` | `output/` | master mixes (and their `.m4a` previews), rendered videos (one per aspect ratio) |
| `/static/backgrounds` | `backgrounds/` | uploaded stage and video backdrops, each kept until the studio that uploaded it replaces or removes it |
| `/` | `frontend/dist` | the built single-page app, plus what `frontend/public` ships: `manifest.json`, `sw.js`, `offline.html`, the icons and `screenshots/` (§3.7) |

With `ALLOWED_HOSTS` set, `middleware.AllowedHosts` answers 400 to a `Host` header that names another host (loopback names always pass), which stops DNS rebinding against an install without a passphrase. Request bodies are capped by `middleware.BodyLimit`: an upload route's own file limit plus 1 MB, else `MAX_JSON_BODY_MB` (default 16). A larger `Content-Length` gets 413 before anything is read, and a body without one is counted as it is read. `SecurityHeaders` sets `nosniff`, `X-Frame-Options: DENY`, a referrer policy, a `Permissions-Policy` that turns off camera, geolocation, payment and USB and leaves the microphone to this site's own pages alone (`microphone=(self)`: practice reads a singer's pitch in the browser, and a page framed from elsewhere gets none), and `Cross-Origin-Opener-Policy: same-origin` on every response, and `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'; sandbox` on `/api/*` and `/static/*` (except the `/api/docs` page), so a JSON body or an uploaded file opened in a tab cannot run script. The studio's own page has no CSP yet: its inline boot script would need a hash. Cache headers come from `http_delivery.cache_control_for`: Vite's hashed `/assets/*` are `immutable` for a year; `/`, `/index.html`, `/sw.js`, `/offline.html` and `/manifest.json` are `no-cache`, so a new build, service worker or manifest reaches open tabs and installed apps; everything else gets none.

Stem, master and rendered video URLs carry a `?v=` version after a re-separation, remix or new render so browsers never play or download a stale file.

| `GET /api/project/{id}/export/{lrc,ass,chord-sheet}`, `…/export/audio/{stem}` | exports; `{stem}` is `instrumental`, `vocals`, `master`, or a vocal part the song has: `lead_vocals`, `backing_vocals`, `male_vocals`, `female_vocals` |
| `GET /api/project/{id}/youtube-package` | YouTube title, description, tags and chapters |

### 2.3 Persistence and concurrency

- **Store.** Projects live in `projects.json`, written atomically with a `.bak` copy for recovery. All writes take `PROJECTS_LOCK`. A project in memory is never swapped for its copy on disk (`merge_disk_projects` only adds projects that memory lacks), but a song can be deleted, or replaced by a new intake of the same link, while a job runs, so background jobs look the project up again before every write instead of keeping a reference.
- **Server settings.** `backend/server_settings.py` keeps the values the owner saved on the Server settings page in `<data dir>/settings.json` (`{"version": 1, "env": {"SONG_LOOP_MODELS": "ltx"}}`), each as the text its environment variable would hold, so the code that reads the variable parses a saved value exactly as it parses one from `.env`. Those readers call `server_settings.env(name)` instead of `os.getenv(name)`: the saved value if there is one (an empty one counts, which is how "off" is saved), else the environment's. Three options that `config.py` parses at import have a function there instead (`max_song_minutes`, `max_album_minutes`, `song_search_sources`), which falls back to the `config` attribute tests replace. The file is read once per data folder and kept in memory, so a save applies at once; it is written through `project_store.write_text_atomically`, the same one-step write as `projects.json`, with a `.bak` copy that a damaged file is recovered from. `services/admin_settings.py` owns what the page offers: the list is `assets/shared/server_settings.json` (shared with the studio), what a setting is *now* is asked of the code that uses it (`READERS`, so the page shows the clamps and defaults the server really applies), what the environment alone gives is the same readers run inside `server_settings.trying({})`, and a change is checked (a default must be among the options its set would then offer, at least one video model, Fast always offered) and saved under one lock, all of a request's changes or none. The module imports nothing from the app at import time: RoFormer's worker imports `separation_presets`, which imports it, on a cloud GPU with neither FastAPI nor a data folder. Thirteen settings go through it; options read once at start-up (job slots, CORS origins, the data folder) and the build-time upload limits do not.
- **Job slots.** `WORKER_SEMAPHORE` (`MAX_CONCURRENT_JOBS`, default 2) bounds intake pipelines, renders, re-separations and background re-alignments. They start through `background_jobs.run_job`, on threads of their own (`JOB_THREADS`), so jobs waiting for a slot never take the threadpool that request handlers share. `lyric_sync.ALIGN_SEMAPHORE` (`MAX_CONCURRENT_ALIGN_JOBS`, default 1) bounds neural alignment passes, which load a large model: pipelines wait for a slot, while a single-line re-align falls back to DSP when the slot is busy.
- **Cancellation.** `active_cancellations` maps keys to `threading.Event`s: `{id}` (pipeline), `{id}_render`, `{id}_reseparate`, `{id}_sync`, `{id}_vocal_split`, `{id}_song_loop`. Deleting a song sets all of them, then removes its files, including staged stems. A route registers a job's event before the song shows the job as busy, and every job (intake, render, re-separation, background re-alignment) removes only its own event when it ends (`background_jobs.release_cancel_event`), so a cancel followed at once by a new request keeps the new job's event. A render requested while a cancelled render is still stopping registers its own event in place of the set one and waits for the old render to end (one render per song at a time, `render_worker._song_render_lock`); the old render then leaves the song's render fields alone (`background_jobs.superseded`). A cancelled render waiting for a job slot gives up the wait at once. A job with no event therefore belongs to an earlier server process: at startup and on every read of a song, its status or the library, a busy intake or a `queued` or `rendering` render with no event under the song's id or track_id, or a `queued` or `running` background job with no event under the id, becomes an error, "Interrupted by a server restart". An intake is settled only when its `heartbeat` is also missing or older than this process's start (`background_jobs.PROCESS_STARTED_AT_MS`), which keeps `seed_demo`'s processing song live; renders are settled on the event alone.
- **Updates.** `scripts/update_when_idle.sh` lets the host restart the server without cutting jobs off (`backend/update_drain.py`). Before it moves to a new commit it reads the newest run of the CI workflow for that commit from GitHub (`GET /repos/{owner}/{repo}/actions/workflows/ci.yml/runs?head_sha=…`, repository taken from the origin URL): only `success` lets it through, a failed run keeps the running version, a run still going is polled for up to `UPDATE_CI_WAIT_SEC`, and when no result can be read (API unreachable, origin not on GitHub, no run for the commit) it updates and logs why. The commit last seen failed or still running is written to `<data dir>/.update_ci_hold`, and for that commit a later call that reads no result stays where it is instead. It then resets to the commit it checked, builds the new image, then writes `<data dir>/.update_draining`; while that file is fresh (younger than `UPDATE_DRAIN_MAX_SEC` plus 5 minutes) the routes that start a long job (`/process` for a new song, `/upload-track`, `/render`, `/reseparate`, `realign-lyrics` with `background: true`) answer 503 with `Retry-After`, right after their `ensure_free_space()`. The server writes the number of keys in `active_cancellations` to `<data dir>/.jobs_active` whenever `run_job` starts or ends a job and every 15 seconds; the script recreates the container once a count written after the pause began is 0, the file is over a minute old, or the limit passes, then writes the commit to `<data dir>/.update_deployed`. That file, not the checkout's HEAD, says what is running, so a call after a failed build or restart tries the update again. The new process removes the marker in `lifespan`. `useUpdateDrainNotice` shows the pause to everyone.
- **Disk space.** `save_projects` returns whether it wrote the store. Request handlers that report an edit as saved (lyrics, title and artist, chords, `/mix` and the custom instrumental) call `save_projects(strict=True)` inside `restore_on_failed_save`: a failed write answers 507 (`OSError`, usually a full disk) or 500 (anything else) and puts the edited fields back in memory, so a reload never shows an edit that the next restart would lose; the instrumental upload also puts back the file an earlier upload left at its path. A delete whose save fails removes the song's files, then removes the song again (a reload from disk may have brought it back meanwhile) and retries strictly; a second failure answers 507 saying the files are gone but the library still lists the song. Background and progress saves stay soft: they log the failure, keep the newest state in memory, and count as a write, so throttled progress saves retry about once a second. `ensure_free_space` refuses new work with 507 while the data folder's disk has less than `DISK_MIN_FREE_MB` free (default 1024, 0 turns it off): `/process` (except a song that is already ready or running), the three uploads, `/render` and `/reseparate`, each after its 404, 409 and request checks (an upload's file-content check needs the file, so it comes after). Edits are never blocked, and when the free space cannot be read the request goes through.

### 2.4 Intake pipeline

`pipeline.run_pipeline` (a song link) and `run_local_pipeline` (upload) move a project through these statuses (the progress bands drive the processing view):

| Status | Progress | Work |
| :--- | :--- | :--- |
| `queued` / `processing` / `downloading` | 5–34 | fetch audio and metadata |
| `separating` | 35–70 | stems at the song's preset (`separate_project_stems`); then the vocal range and chords start alongside the rest |
| `fetching_lyrics` | 72 | wait for the lyric lookup (LRCLIB / NetEase / syncedlyrics), or parse the custom lyrics |
| `aligning` | 82–91 | `sync_lyrics` (DSP, then neural when available); then, when the neural aligner timed the song, `repeat_fill.fill_repeats` adds the repeats the lyrics left out, and `voice_parts.assign_voice_parts` assigns parts by voice while every line is still Singer 1 |
| `mixing` | 92 | first master mix |
| `ready` | 100 | the studio opens |

Two things overlap the steps in the table. The lyric lookup only needs the title, artist and length, so it starts on a thread of its own (`LyricsPrefetch`) as soon as those are known (after the download, or after an upload is transcoded) and runs while the stems are separated; `fetching_lyrics` then just collects its result, and a failed lookup ends the song with its error as before. Pasted lyrics skip it. And when the song's preset runs on the cloud GPU and its stems are not cached (`Separator.has_cached_stems`), `warm_separation_gpu` asks Modal for a GPU when the intake begins and again on download progress (see Cloud GPU in §2.6).

**Song links** (`services/media_links.py`, sites and domains in `backend/assets/shared/media_sites.json`). `parse_media_link` turns a pasted link into its site, the address yt-dlp gets and a file-safe track id, offline: a YouTube video id (`TrackDownloader.extract_video_id`), else `<site>-<id>`, the Vimeo video number or the first 12 hex digits of a SHA-1 of the link's song part (SoundCloud `user/track`, Bandcamp `artist/track`, Archive `identifier/file`), so the same song pasted with other tracking parameters, case or host (`m.`, `www.`) gets the same id. The id names the song's audio in `downloads/`, its stems folder and, as at YouTube intakes, the project, so `/process` finds a song already made or running from the link alone. A link to a supported site that is not one song (a SoundCloud profile, set or likes page, a Bandcamp album, a Vimeo channel, an Archive search) raises `UnusableLink`, whose message says what to paste instead; `ProcessRequest`'s validator returns it as the 422 detail, and a link to any other site gets one naming the supported sites. `/process` stores the link as the project's `url` from the start. The downloader keeps YouTube's path as it was (player-client retries, metadata refresh for cached audio); another site's link goes through `_download_from_site`: `extract_info(download=False)` first, a playlist of one unwrapped and a longer one refused with `UnusableLink` ("holds N recordings", an Archive item of a whole album or concert) before anything downloads, then `process_ie_result(download=True)` with `outtmpl` `<track id>.%(ext)s` (the sites' own ids can collide and Archive ones hold slashes). Audio already on disk is reused and its metadata refreshed when the site answers, but only audio whose download finished: a `<track id>.wav.unfinished` marker sits beside the WAV while yt-dlp writes it, a download that raises deletes its partial WAV, and a WAV that still has its marker (the server stopped mid-download) is deleted and downloaded again (`fresh_download`, `cached_audio`). Before any download, `refuse_unsuitable` refuses a live stream and a recording longer than `MAX_SONG_MINUTES` (default 60, 0 lifts the limit) with `UnusableLink`: YouTube's path passes it to yt-dlp as `match_filter`, which runs on the metadata, and the other sites' path calls it between the two steps. The artist is yt-dlp's `artist`, else the recording's creator (the Archive's `creators`), else the uploader, never an email address (`track_artist`). yt-dlp needs a Vimeo login for most videos, so those fail with its sign-in error, which the failed screen explains.

**Whole albums** (`backend/album_pipeline.py`, `services/album_tracks.py`, `services/album_audio.py`, `routers/albums.py`). A pasted link is checked for a whole album on the metadata yt-dlp reads before it downloads: `downloader.intake_filter` is YouTube's `match_filter` (and is called between the other sites' two steps) and raises `AlbumDetected` when `looks_like_album` holds (at least `ALBUM_MIN_SECONDS`, 600, long, not live, and either album words in the title ("Full Album", "Full EP", "Álbum Completo") or three or more chapters with a median length of a minute), otherwise it runs `refuse_unsuitable`. It never runs for a song matched from a catalog (`file_stem`) or once the album is being made as one song (`detect_album=False`, from the project's `album_whole`). `run_pipeline` hands the album to `open_link_album`: an album longer than `MAX_ALBUM_MINUTES` (default 120, 0 lifts it) is refused, otherwise `download_album_audio` downloads it once in the format the site served (`<track id>.album.<ext>`, its thumbnail `<track id>.<ext>`, the same player-client retries, a `.album.unfinished` marker while it downloads, one download at a time per album). `identify_tracks` reads the loudness of the whole album through FFmpeg in chunks (mono 8 kHz, one dBFS value per 50 ms, `loudness_envelope`) and lists the songs: from the chapters (`usable_chapters`, `tracks_from_chapters`: track numbers and timestamps dropped from the names, "Artist - Song" chapters giving the album artist or, on a compilation, each song's own), each boundary moved to the middle of the quietest stretch within 2.5 s (`snap_cuts`); else from the album's track list in a catalog (`find_catalog_album`: Deezer's album search and track lists, the iTunes Store's album search and lookup, of the `SONG_SEARCH_SOURCES`, the album of the same artist and name whose songs add up to the recording's length within 4 % or 20 s, the closest when several do; a deluxe edition with bonus songs is not the recording), the songs placed end to end and each cut looked for within 12 s one song's length after the cut before it (`place_cuts`), so the silence an upload adds does not pile up; else from the pauses (`split_at_pauses`: stretches a second or more long, 32 dB under the loud passages and under -40 dBFS, at least `SONG_MIN_SEC`, 45 s, apart, as unnamed "Track N" songs). The artist and album name come from yt-dlp's `artist` and `album`, else the title split at its dash with brackets, album words, years and "HQ" removed (`album_names`). The project then rests with status `album`, the album's title, artist, length and cover, and `album` (`kind`, `url`, `source`, `catalog`, `audio_file`, `tracks`). Uploads of ten minutes or more are checked the same way by `open_upload_album`, from the file's own chapters (`file_chapters`, FFprobe, read before the transcode), the catalog album of the title and artist given, or at least three songs told apart by their pauses; anything else goes on as one song. `POST …/album/songs` creates a project per picked song (`<album id>-tNN`, `album_track`: album id and title, number, start, end, and how to fetch the album again) and starts `run_pipeline` for it, whose download step is `album_pipeline.song_audio`: the album's audio (downloaded again if it is gone, a link's; an upload's must still be there) is cut from start to end with FFmpeg into the song's WAV (`cut_song`), and the song keeps its own title, the album's artist (or its own on a compilation) and the album's cover (`thumbnail_path` shared, so deleting one song keeps it for the others; deleting the album deletes its compressed copy). The lyric lookup gets the song's title, artist and cut length like any other song.

**Streaming links** (`services/song_lookup.py`). Spotify, Apple Music, TIDAL and Deezer are `lookup` sites in `media_sites.json`: their audio cannot be downloaded, so `parse_media_link` takes the service's song id (`source_id`; Spotify's track id after an optional `/intl-xx/` or `/embed/`, Apple's `?i=` on an album page or the id of a song page, TIDAL's track id from `/track/`, `/browse/track/` or `/album/<id>/track/`, Deezer's from `/track/` after an optional language) and names the project `spotify-<id>`, `applemusic-<id>`, `tidal-<id>` or `deezer-<id>`; a Deezer share link (`link.deezer.com/s/<code>`) has no song id until it is followed, so it is named `deezer-s<digest of the code>` and `song_lookup` follows its redirect; albums, playlists and artists raise `UnusableLink` with how to copy a song's link. At download time `fetch_song_info` reads the song (`SongInfo`: title, artists, length) with `requests` (10 s timeout): Spotify's track page (`og:title`, `music:musician_description`, `music:duration`; the artist from `og:description` when the musician tag is missing), Apple's iTunes lookup API (`lookup?id=…&country=<the link's country>`), TIDAL's track page (its `MusicRecording` JSON-LD, else the `<title>` "Song by Artist on TIDAL"), Deezer's track API (`api.deezer.com/track/<id>`, every credited artist from `contributors`; it answers errors with status 200 and an `error` body, code 800 meaning no such song). A 404, another HTTP error, an unreachable service or a page without title and artist raise `SongNotFound` with a message for the user. `find_on_youtube` searches YouTube for "artist title" (`search_tracks_or_raise`, 10 results; a failed search is tried once more, then raised as "YouTube search failed") and ranks the results by `match_score`: title similarity of at least 0.6 and artist similarity of at least 0.5 (`LyricsService.calculate_similarity` on `normalize_track_metadata` of both sides, the upload's title split either way round, the channel without "- Topic"/"VEVO" or the artist named in the title also counting as the artist), up to 20 points for length (full within 4 s, ruled out past 15 s), 5 for the artist's own channel or a "- Topic" upload; an upload whose title names a version the song's own title does not (`OTHER_VERSIONS`: live, cover, karaoke, remix, sped up, slowed, instrumental, acoustic…) never matches. No match raises `SongNotFound` ("Could not find … on YouTube"), so a song is refused rather than guessed. `TrackDownloader._download_by_lookup` tries the best three matches in turn (`LOOKUP_ATTEMPTS`), stopping at a cancel or YouTube's bot check, and downloads with `file_stem` set to the song's track id, so its audio, stems, master mix and renders are its own even when a song from the same video exists. The song keeps the service's title and artist (the lyric lookup's input), its link as `url` (Try again looks it up again) and `song_match` (the service's site, title, artist and length, and the upload's id, title and URL), which the song check-up shows (`utils/songCheckup`: a tip when the upload's length differs from the service's by more than 4 s).

**Song search** (`services/song_search.py`, `routers/search.py`). `POST /api/search/songs` turns typed words into songs, not videos: `search_songs` asks Deezer's search API and the iTunes Search API (both public and keyless; `requests`, 2 s to connect and 3.5 s to read, 25 songs each) on a small thread pool and answers within `SEARCH_DEADLINE_SEC` (5 s) with whatever arrived. Misspellings are handled in three layers. Both catalogs search loosely themselves. YouTube's search suggestions (`suggestqueries.google.com`, the `suggest` source) respell the query: `pick_correction` takes the first suggestion that is the same words (every word of each matches a word of the other within the typo allowance, at least one typed word is a misspelling; a suggestion equal to the query means it is spelled right, and one that only completes the last word or adds "lyrics" is no correction), and the corrected words are searched too. When no suggestion respells it, `respell_from_songs` replaces each misspelled word with the word the first ten songs found use and the catalogs are asked once more. Deezer is asked for the typed and the corrected words; the iTunes Store, which allows about twenty requests a minute, only for the best spelling known. Then the songs are ranked here, not in either catalog's order (`rank_songs`): `merge_songs` folds copies of one recording together (the same title once featured credits, soundtrack notes and remaster or edition words are dropped (`title_key`), the same act (`same_artist`: the same name or the first name of a list, so a tribute act named after the artist stays apart) and lengths within `SAME_RECORDING_SEC`, 5 s), keeping every catalog's link, the plainest title, the earliest year, the highest popularity and Apple's preview link (Deezer's expire after 15 minutes); `score_song` adds 55 × the share of the typed words the title, artist and bracketed notes explain (`word_similarity`: equal, a beginning, or within `_typos_allowed` edits, one for 3 to 5 letters, two up to 9, three beyond, neighbours swapped counting once), 15 × the share of the title the words name, 10 × the share of the artist's name (a word that names the artist does not count for the title), 20 × popularity (Deezer's `rank`; a song only iTunes lists is judged by its position), 5 for the catalog's own order and 3 when both list it, minus 14 per kind of other version the title's brackets name (`version_labels`: live, remix, acoustic, cover, karaoke, instrumental, demo…, read from brackets and a dash suffix only, so "Live Forever" is a plain song) unless the words ask for it, 6 for any other bracketed variant ("Radio Edit", "Pianoforte") and 18 for a sound-alike act (karaoke, tribute, lullaby, workout names) the words do not name; when the words spell out a song's whole title and its act (`named_acts`; the first act of a shared credit is enough), a song by anyone else loses 12, or 18 when its act is named after the artist ("Hello I'm Adele"), so a cover titled "Wonderwall Oasis" lists below Oasis's own live takes. When neither catalog's first two picks are explained by the words (`names_songs`, under half), the words are a line of the lyrics rather than a name, and the catalogs' order leads instead. Answers are cached for 5 minutes (256 queries); a catalog that answers 403 or 429, or Deezer's quota error, is skipped for a minute; a failed or slow catalog costs only its own songs, and an answer from no catalog is not cached. The route marks results that are already in the library (`_in_library`: a ready or running song with one of the result's catalog ids, or the same recording by name (`title_key`, so a live or acoustic take is never the library's studio recording), the same artist and a length within 15 s) and returns each song's `url`, a Deezer link when Deezer lists it and an Apple Music link otherwise, which `POST /api/process` starts like a pasted link: the lookup reads the song again and matches it to a YouTube upload, so a searched song gets the catalog's title, artist and length and never another version. `SONG_SEARCH_SOURCES` picks the services (`deezer`, `itunes`, `suggest`; `none` turns the catalog search off) and `SONG_SEARCH_COUNTRY` the iTunes store. With no catalog configured or answering, `sources` is empty and the studio lists YouTube uploads from `POST /api/search` (`downloader.search_tracks`, yt-dlp's `ytsearchN:`), which it also offers under the songs for a recording the catalogs do not have.

The vocal range and chords are not a step: `analyze_project_stems` starts each on a thread of its own once the stems exist, and the song goes `ready` without waiting for them. The studio fetches whichever is missing when the song opens (`useProjectChords`, `useVocalRangeBackfill`); those requests wait for the analysis already running instead of starting another (see Song analysis in §2.8). A failed analysis is logged and backfilled on the next request. The melody (§2.8) is not analysed at intake at all: most songs are never practised, so it is worked out when practice first asks for it. The processing view's stepper has four steps: intake, separation, lyrics, mixing.

### 2.5 Background jobs on a finished song

The three jobs keep their state on the project (`separation_job`, `sync_job`, `vocal_split_job`: `id`, `status` queued/running/done/error/cancelled, `progress`, `detail`, `error`, timestamps), so the studio just polls the project's status (`GET /api/project/{id}/status`). `background_jobs.conflict_reason` stops a job from starting while another runs or while the song is still processing (409; a re-separation and a vocal split also wait for a video render), and a job left `queued` or `running` by a server restart is marked as interrupted at startup and on the next read.

**Re-separation** (`reseparation.py`). Separates into `stems/.staging/<audio_id>/<job>` (progress 0–80), swaps the new stems and their `separation.json` record in with `os.replace` (dated at the swap, so mixes of the old stems are not reused; the record is replaced even on a downgrade), keeps a custom instrumental, refreshes the vocal range, re-detects chords only when asked (or when there are none), optionally re-times the lyrics (lines timed by hand keep their timing when the job has `keep_manual`; everything is kept as it is if someone saves lyrics meanwhile, compared by the same digest as below), and renders a new versioned master mix. A cancelled or failed run leaves the song exactly as it was, and removes its staging folder; the folders of runs a server restart cut off are deleted at startup.

**Vocal split** (`vocal_split.py`, `services/vocal_parts.py`). Runs one RoFormer plan over a vocal stem through `AudioSeparator.split_vocals` (no cache, no fallback chain: there is no Demucs equivalent) into the same staging folder, then `vocal_parts.install` moves the two stems beside the vocals and records how they were made in `vocal_parts.json`. `lead_backing` splits `vocals.wav` into `vocals_lead.wav` and `vocals_backing.wav` with a "karaoke" model, whose outputs carry the usual vocals/instrumental tags, so the worker and the deployed cloud function run it unchanged. `male_female` splits the lead (the whole vocals when there is no current lead/backing split; the record keeps which) into `vocals_male.wav` and `vocals_female.wav` with a model whose outputs are tagged "male" and "female": its plan carries `first_tags` / `second_tags`, which `separator._command` and `remote_separation.run_remote` pass to the worker (`--first-tags`, `--second-tags`) only for such a plan. Which parts a song has is read from the files, never from the project: a pair counts while both files hold audio and are no older than their source (`vocal_parts.current_parts`), since a stems folder can be shared by two songs and outlives an intake retry. The job takes parts that are already current without running the model, an intake adopts them, and the project's `vocal_splits` is a copy for the studio. Installing lead/backing deletes male/female (their source is replaced); replacing `vocals.wav` (re-separation's swap, an in-place separation) deletes every part, and the re-separation says so in a warning. When the song's stored `vocal_levels` ask for the new parts, the job mixes the master again as its last step. A cancelled or failed run changes nothing.

**Background re-alignment** (`realignment.py`). The route works out the lyrics first (so input errors come back as 400s), then queues `sync_lyrics` with the server's configured engine. When it finishes, the lines are stored only if nobody saved other lines meanwhile (a digest of the lines is compared); otherwise the job ends with "your edits were kept". Re-timing existing lines keeps word timing that came with the lyrics file (`align_method: "lrc"`) and, when the request sets `keep_manual` (the studio always does), the timing of lines whose words were timed by hand (`"manual"`, `lyric_sync.prepare_existing_lines`). A manual line whose words are only the editor's even spread over the line (`words_spread_evenly`: back to back, each in proportion to `wordSpreadWeight`, as line-by-line tap-to-sync, new lines and retyped text leave them) is timed again: only its start and end were set by hand. A one-word line is never such a spread: every edit sets the line to its word, so an ad-lib timed by hand is kept.

**Song loop** (`song_loop.py`, `services/song_loops.py`, `services/remote_song_loop.py`). A fourth job, `song_loop_job`, makes the song's loop: a looping background video drawn from its lyrics. It exists only with `SONG_LOOP_REMOTE=modal`, since the models need a large GPU and packages the server does not install. The job sends the lyric lines (or the scene the request typed) with the title and artist to the Modal function `song_loop`, which runs `workers/song_loop_worker.py`: a language model (Qwen3 4B) writes one scene of scenery with no faces or lettering unless a scene was typed, a video model (the request's `model`, else `SONG_LOOP_MODEL`: Wan 2.2 TI2V 5B, which the studio calls Best, or LTX-Video 0.9.7 distilled, Fast; `SONG_LOOP_MODELS` limits which are offered) draws a few seconds of it, and FFmpeg fades the clip's first second over its last (`loop_filter`), which leaves a loop whose last frame leads into its first. That fade shows as a double image when the view moved during the clip, so both prompts ask for a fixed camera; Wan 2.2 keeps to it and LTX-Video often does not, which is why Wan is the default although it takes 7 to 8 minutes to LTX's 2. The worker's stderr events feed the same `ProgressTracker` as a separation. What comes back is written as `<id>_loop.part.mp4` in the output folder, checked with ffprobe (a video of a sane size and length, no larger than an uploaded background), and only then moved over `<id>_loop.mp4` and recorded as `song_loop` (`url`, `prompt`, `written_from`, `model`, `seed`, size and length), so a failed or cancelled run keeps the loop the song had, a part file is swept at startup with unfinished renders, and deleting the song deletes the loop with its other output files. Unlike the three jobs above it changes nothing they read, so it neither waits for them nor blocks them (only a second loop for the same song is refused, and a song that is not `ready`), and it takes no `WORKER_SEMAPHORE` slot: the server only waits. Loops are made one at a time (`SONG_LOOP_SEMAPHORE`), which bounds GPU spend. A render whose `background_style` is `loop` gets the file as its custom background (`render_worker`), so everything after that is the uploaded-video path; without a loop the style is unknown to the renderer and the cover art is drawn.

**Show videos** (`services/show_videos.py`, `routers/show.py`). A show (§3.5) plays YouTube karaoke videos on the stage window in YouTube's embedded player. Some uploaders turn embedding off (the largest karaoke channels among them), and such a video plays only on youtube.com. `listing(video_id)` asks YouTube's oEmbed endpoint, which answers 200 with the title and channel for a video that can be embedded and 401 for one that cannot; the answer is kept in memory (an hour, a minute for none), and the host screen asks when a video joins the queue. For the ones that cannot be embedded, `POST …/fetch` starts `run_fetch` as a background job: yt-dlp downloads H.264 with AAC where YouTube has them, 720p at most, into `<data dir>/show_videos/<id>.mp4` (written beside it as `<id>.fetch.mp4` and moved into place). yt-dlp's own choice of YouTube clients is tried first, since it is the one offered separate picture and sound streams (720p); the song downloader's clients come after and give a 360p file. `refuse_unsuitable` refuses live streams and recordings over `MAX_SONG_MINUTES` on the metadata. Fetches run one at a time (`FETCH_SEMAPHORE`) and register a cancel event (`<id>_show_video`), so an update waits for one. Whether a copy exists is read from the file, never from memory: `_jobs` only holds what is being fetched and what failed last. The folder is kept within `SHOW_VIDEO_CACHE_GB` (3, 0 for no limit) by removing the least recently used copies (serving a copy touches it; the one just fetched is never removed), and `SHOW_VIDEO_DOWNLOADS=0` turns the fallback off (`capabilities.show.video_downloads`). The route takes the video id alone, never a link, because the id names the file.

**Song requests** (`services/show_requests.py`, `routers/show.py`). A show's host files a song it could not find, neither as a karaoke video nor in the library; the owner makes it later, or does not. A request is the words the host typed (`song`, 120 characters at most), the first eight `singers` who asked, the name of the night it was last asked at (`show`), how often it was asked for (`count`) and when it last was (`requested_at`). The list is `<data dir>/show_requests.json` (`{"version": 1, "requests": [...]}`, oldest first), read on every call and written atomically (`project_store.write_text_atomically`); nothing is held in memory, and a file that cannot be read counts as an empty list. Asking again for a song on the list (the words compared without case or spacing) counts that request once more, adds the singer and moves it to the front. The list holds `MAX_REQUESTS` (200) songs and answers 409 to another: a show sign-in can add to it, so it must not grow without limit, and dropping the oldest would let new requests push real ones out. Nothing is made from a request by itself.

### 2.6 Stem separation

**Presets** (`separation_presets.py`):

| Preset | Engine | Models | Parameters |
| :--- | :--- | :--- | :--- |
| `fast` | Demucs | `htdemucs` | `--shifts 1 --overlap 0.25 --int24 --clip-mode clamp` (Demucs 4.1+) |
| `balanced` | RoFormer | `vocals_mel_band_roformer.ckpt` | overlap 2 |
| `best` | RoFormer ensemble | Mel-Band + `model_bs_roformer_ep_317_sdr_12.9755.ckpt` | overlap 4, waveform average |

Availability is decided without importing PyTorch: package metadata (`find_spec`, versions) plus whether the weights are cached or may be downloaded. `separate_stems(audio_path, track_id, model_name, duration, progress_callback, cancel_event)` resolves a preset (or a raw Demucs model name), walks the fallback chain best → balanced → fast, skips plans that cannot run, and falls back on any failure that is not a cancellation. The result includes provenance (`preset`, `engine`, `models`, `label`, `requested`, `fallback_reason`, `elapsed_seconds`, `separated_at`), stored on the project as `separation` and beside the stems as `separation.json` (written to a temp file and moved into place; the old record is removed before new stems replace the old ones). Valid cached stems are reused without running anything when their record's preset ranks at or above the request (`preset_rank`: fast < balanced < best; raw Demucs models rank with Fast), and the reused record reports the new `requested` with no `fallback_reason`. Stems without a record (made before records were kept, or whose record is unreadable) count as Fast, so they are re-separated once when a song is re-processed at Balanced or Best. A retried link intake (the same song's link added again after a failed, cancelled or interrupted one) replaces the song, so `/process` first writes the old song's `separation` as the record of valid stems that have none (`adopt_provenance`; a readable record always wins), and stems its old song knew as Best or Balanced are reused. Below the request only the better presets are tried, and if none of them can run, or all fail, the cached stems are kept with the reasons as `fallback_reason` instead of being replaced by a cheaper fallback (status "Kept the earlier stems").

**Engine processes.** Both engines run as child processes with stdout discarded and stderr parsed line by line (`ProgressTracker`): tqdm bars, model download bars ("Downloading model weights… (N%)") and JSON events. `ProcessWatchdog` terminates (then kills after 10 s) a process that is cancelled, exceeds `SEPARATION_TIMEOUT_SEC`, or prints nothing for `SEPARATION_STALL_SEC`. Errors read "Demucs failed (exit N): …" or "RoFormer separation failed …" with a friendly hint (out of memory, disk full, weights missing) and the last lines of stderr.

**Cloud GPU** (`remote_separation.py`, `gpu/modal_app.py`). With `SEPARATION_REMOTE=modal`, RoFormer plans are spawned on the deployed Modal function instead of a local process. It runs the same worker on the first free GPU (`A10G,L40S,L4,T4` by default, fastest first since billing is per second), keeps weights in the `karaoke-models` volume, and puts a start marker and then the worker's stderr on an ephemeral Modal queue, which feeds the same `ProgressTracker`; the stems come back as the call's result. After a successful separation the function also runs the CTC worker's emission-only mode on the new vocals (MMS weights in the same volume, at most 5 minutes) and returns the emission with the stems; `remote_separation` keeps it with `emission_cache.store`, keyed by the vocals' bytes (not for a vocal split, `keep_emission=False`: lyrics are never timed on a part). A plan with stem tags (the male/female split) adds `first_tags` and `second_tags` to the call; they are sent only then, so an app deployed before it knew them keeps serving every other job, and fails only that split until it is deployed again. If that step fails the stems still come back and the first sync listens on the server as before. Availability then means the `modal` client and credentials are present (checked offline). Cancel, `SEPARATION_TIMEOUT_SEC` and `SEPARATION_STALL_SEC` cancel the remote call. Modal also stops the function at the limit it was deployed with (`SEPARATION_REMOTE_TIMEOUT_SEC` at `modal deploy`, 1800 s by default), whatever the server's setting; that ends the job as a timeout whose message names the deploy-time limit (`RemoteOutcome.remote_limit`). If the service is unreachable, or no GPU starts the job within `SEPARATION_REMOTE_QUEUE_SEC`, the job raises `RemoteUnavailable`, the other cloud presets are skipped and Fast runs locally. Time estimates use `REMOTE_REALTIME_FACTORS` plus a fixed 30 s for queueing, start-up and transfers, and capabilities report `runs_on: "cloud-gpu"`. `remote_separation.warm_up` spawns `separate(warmup=True)`, which returns at once, so a GPU container boots while the song downloads; the intake pipelines call it (on a background thread) when they start and on download progress, at most every 20 s, which is under the container's 30 s `SEPARATION_REMOTE_SCALEDOWN_SEC`, so one container stays up through a long download. `SEPARATION_REMOTE_PREWARM=0` turns it off.

**RoFormer worker protocol** (`python -u -m backend.workers.roformer_worker`):

```
--audio IN --out DIR --models M1 [M2] --overlap N --model-dir D --allow-download 0|1
[--ensemble avg_wave] [--download-only]
```

It runs one `audio_separator` pass per model into `DIR/passN`, averages ensemble stems, and writes `DIR/vocals.wav` and `DIR/no_vocals.wav`. Stderr carries `{"event": "stage" | "download" | "error", …}` lines. Exit codes: `0` ok, `2` usage, `3` weights missing (downloads disabled), `4` import error, `5` failed.

### 2.7 Lyric sync

**Lyrics** (`lyrics.py`). LRCLIB first, then `syncedlyrics` in a bounded executor; untimed results count as plain lyrics. A synced LRCLIB match is taken at once only when its length is within 10 s of the audio (`DURATION_MATCH_SEC`; a query without a duration returns any version of the song), and once every query is done the best-scoring of the search's best hit and the exact matches wins; a search hit for another song (`is_related`) never does, nor does another artist's song under another name (`is_other_artists_song`: Guerilla Black's "You're The One" for Imperial Teen's "You're One"; a cover with the song's very name still counts), and neither takes the early return. Linked songs are looked up by yt-dlp's `track` when it has `track` and `artist` (YouTube Music, "- Topic" uploads, Bandcamp, most SoundCloud tracks), uploads by the file name as uploaded. LRC parsing honours `[offset:]` (positive means earlier) and enhanced `<mm:ss.xx>` word tags. A line without word tags ends at the next line, a blank timestamp, or once its syllables could have been sung (`sung_line_seconds`: 1 s + 0.5 s per syllable, 2.5–8 s), whichever comes first; lines used to run on to the next one, which made the short lines of slow songs eight seconds long. Plain text drops section headings such as `[Chorus]`; both formats drop credit lines (`作词 : …`, `Written by: …`).

**Choosing a version.** When yt-dlp gives no `artist` and no creator (the Internet Archive's), the artist is only the uploading channel (`downloader.track_artist`), and a title "Artist - Song" is split into its artist and song (`extract_canonical(..., artist_is_uploader=True)`) as long as the dash survives noise cleaning, so "Song - Remastered 2011" keeps its name. Candidates are compared by their song names too (`candidate_song_name`: a leading "Artist - " or "Album - " and version or featuring clauses, even cut off, are dropped), and `score_candidate` subtracts `lyric_quality`'s penalties for a sloppy file (`QUALITY_PENALTIES`: mostly capitals, a line over 120 characters, "x2" markers, translator's notes, three or more lines in the last two seconds). Similarities and song names are cached. When the synced lyrics LRCLIB gives look like a file that writes repeats once (`writes_repeats_once`: a short line comes back and a stretch of 15 s or more between lines holds none), NetEase is asked through `syncedlyrics` (`providers=["NetEase"]`, within `SYNCEDLYRICS_TIMEOUT_SEC`), and its lyrics are used when they are the same song with at least 1.3 times the lines, reach as far into the song and are no sloppier (`is_fuller_transcription`). Results carry `source_id`, the LRCLIB listing used, which the project keeps as `lyric_source_id` (also when the studio applies a listed version, through `realign-lyrics`' `lyric_source_id`).

**Tidying** (`lyric_cleanup.clean_fetched_lines`, applied by `fetch_lyrics` to fetched lines; the raw text stays as fetched). In order: a translator's header in the second half of the song ends the lyrics and a final run of lines under 0.4 s each goes; long explanatory notes in parentheses and "x2"-style markers come off lines; a line over 70 characters or 14 readable words (a CJK character is a token but not a word to read) is split at the natural break nearest its middle, never inside parentheses, keeping its words' timing (`split_long_line`); a CJK line followed by Latin text in parentheses keeps that romanization as `romaji` and its words become its characters (`split_romaji`); and an all-caps song is put into sentence case (`sentence_case_lines`). Lines are numbered again from 0.

**Orchestrator** (`lyric_sync.sync_lyrics(vocals_path, lines, *, lyric_data, engine, progress, cancel_event)`):

1. **DSP pass.** `aligner.align_lyrics(vocals_path, lines)`. Plain lyrics get a second, timed pass that snaps each line to its sung phrase (`ALIGN_REFINE_PLAIN`).
2. **Engine choice.** `ALIGNMENT_ENGINE` auto / ctc / dsp. Neural alignment needs torch and torchaudio 2.10+ and the MMS model (cached, or downloadable when `ALIGNMENT_ALLOW_DOWNLOAD=1`).
3. **Neural pass.** Every line except the kept ones (word timing from the lyrics file, hand-timed lines kept by `keep_manual`) goes to one worker process, each with a window around its DSP timing (0.75 s before it and 0.75 s after it, 2 s for timed lyrics, split halfway into the gaps), waiting for an `ALIGN_SEMAPHORE` slot. With three or more such lines and `ALIGNMENT_SONG_PASS` on (the default) the request also asks for the **song pass** (protocol version 2): the worker runs the model once over the whole stem, aligns the windows on slices of that emission, and force-aligns all the lines together, in order, as `* line * line * … *`, so a line is found wherever it is sung, not only near the DSP estimate. Its baseline `null_score` is the median score of the same lines with scrambled letters.

   **Saved emission** (`emission_cache.py`). The model's output over the whole stem (the emission, about 1.5 MB for a 4-minute song) depends only on the vocals, so it is kept in `<data dir>/alignment_cache/mms_fa-v1-<sha256 of the vocals>.npy`, the 200 most recently used files. Every request names that file (`emission_cache`); when it holds a usable emission the worker never loads the model and aligns both versions on it, so a re-sync, `realign-lyrics` or `realign-line` on the same stem only runs the alignment. A version 2 run that had to listen to the song itself saves the file. With `SEPARATION_REMOTE=modal` the cloud GPU computes it right after the stems (see 2.6), so even a new song's first sync skips the model on the server. Keying by content means staged, swapped or moved stems need no bookkeeping, and new stems never pick up an old emission; bump `CACHE_VERSION` if the model or chunking changes.
4. **Anchors** (`lyric_anchors.plan`). A song-pass line is an anchor when it placed 70% of its words, has at least 6 letters, is neither squeezed nor stretched, and scores well against the baseline n: strong from max(0.15, 3.5 n), weak from max(0.08, 2 n). Model scores depend on the stem, and the right lyrics beat the scrambled ones several times over where the wrong lyrics only about double them. For timed lyrics each candidate's shift from the lyrics file must agree (within 0.4 s) with a neighbour's, or weak ones must form a run of three that agrees; runs of agreeing shifts are the `offset_segments`, and a segment of fewer than three anchors more than 5 s from its neighbours is dropped as a wrong instance (a chorus matched in the wrong place). For plain lyrics only strong lines anchor. The song's median line score must reach max(0.1, 3 n) and at least max(3, 25%) of its lines must anchor, or the plan is `rejected` and the song is timed as without it.
5. **Merge.** Without anchors, per line, neural word timing replaces the DSP estimate when the line aligned, its score is at least `ALIGNMENT_MIN_CONFIDENCE` (0.45) and at least 70% of its words were placed; missing words are shared out between neighbours and timing stays monotonic. With anchors (`lyric_sync.place_with_anchors`) an anchored line takes its song-pass timing, never widened back to the DSP span (for timed lyrics, when the DSP start agrees with it within 0.5 s, the line keeps the DSP and window result, which are a little more precise there); other lines take a confident neural result that fits between their fixed neighbours and starts within 1.5 s of where the anchors put the lyrics file's line, then the DSP line when it is already within 1 s of there, then the song pass's own placement between the anchors (with its low score, so it stays under review; never for a plain line before the first anchor, where nothing but the song's start bounds it and an unsure model puts it on an intro's stage talk or count-in), then the DSP line moved there; plain DSP lines that fall outside their gap are spread over it, a run before the first anchor from where the DSP pass heard its first line rather than from 0 s, and no line overlaps the one before it. Lines with word timing from the lyrics file keep it, and lines timed by hand that `keep_manual` kept are copied back from the input unchanged (the DSP pass may have shifted or rebuilt them) and never go to the neural worker. If the worker fails, the whole song keeps the DSP timing and the reason is recorded; a failed or skipped song pass keeps the window results.
6. **Confidence** (`sync_confidence.py`). Vocal activity and onsets are measured once per stem (10 ms grid, cached by path, size and mtime). DSP lines score 0.5 × coverage + 0.5 × onset agreement (Gaussian, σ = 60 ms); neural lines blend 0.6 × model score with 0.4 × that evidence (an anchor's model score counts from 0.6, reaching 1 at the song's strong score); lyrics-file lines keep at least 0.9; no-audio fallbacks get 0.2.
7. **Output.** Lines gain `confidence` and `align_method` (ctc, dsp, lrc, fallback; the editor adds manual, and kept hand-timed lines stay manual, without a confidence). The project gets a `sync_report` (engine, fallback reason, line counts per method including `lines_manual`, the song pass's status `song_pass` (ok, rejected, skipped, failed, off; null without the neural engine) with `song_pass_reason`, `lines_anchored`, `lines_relocated` (more than 1 s from the DSP estimate) and up to 8 `offset_segments` ({first_line, last_line, offset, anchors}), low-confidence count, mean confidence, elapsed time) and `lyric_timing` (`source_word`, `source_line`, `aligned`, `none`). `is_synced` stays false for plain lyrics; the UI reads `lyric_timing`. The report also holds `vocal_regions` (stretches of strong vocals: within 20 dB of the stem's loud level, bridging pauses under 0.5 s, at least 0.5 s long) and `uncovered_vocals` (those parts of at least 2.5 s that no line, widened by 0.3 s, covers; `backend/assets/shared/uncovered_vocals.json`), which the studio redoes live as lines change. After the intake's alignment (§2.4), `repeat_fill` tries each short line the song repeats in the uncovered stretches with the neural aligner, one batched worker call per round and four rounds at most, and adds a match placing every word with a score of at least 0.7 as a line with `added: "repeat"` (the report then gains `lines_added_repeats`); and `voice_parts` takes each line's median pitch, pitched share and brightness on the stem, splits the lines into two clusters, and accepts the split only with a silhouette of at least 0.35, medians at least four semitones apart and two or more lines each, the longer-singing voice staying Singer 1 (`project.voice_parts` records the outcome). Lines may carry `romaji` and `added`, kept through saves; projects may carry `part_names`.

**CTC worker protocol** (`python -u -m backend.workers.ctc_align_worker --request REQ.json --response RES.json`):

```jsonc
// request
{"version": 1, "audio": "/abs/vocals.wav", "model_dir": "/models/mms_fa", "allow_download": true,
 "lines": [{"index": 0, "window_start": 9.45, "window_end": 14.6, "words": ["every", "window", ""]}]}
// response
{"version": 1, "model": "MMS_FA",
 "lines": [{"index": 0, "status": "ok", "error": null, "line_score": 0.83, "star_ratio": 0.12,
            "words": [{"start": 10.21, "end": 10.58, "score": 0.91}, {"start": 10.6, "end": 11.0, "score": 0.77}, null]}]}
// either version may name the saved emission (read when usable, written by a version 2 run that listened itself)
{"version": 1, ..., "emission_cache": "/data/alignment_cache/mms_fa-v1-<sha256>.npy"}
// version 2 adds the song pass to the request ...
{"version": 2, ..., "song": {"lines": [{"index": 0, "words": ["every", "window", ""]}]}}
// ... and to the response (the line results are there either way)
{"version": 2, ..., "emission": {"frames": 13450, "seconds_per_frame": 0.02, "chunks": 14, "seconds": 61.2, "cached": false},
 "song": {"status": "ok", "error": null, "null_score": 0.05,
          "lines": [{"index": 0, "status": "ok", "line_score": 0.41, "start": 10.2, "end": 11.0, "words": [{...}, {...}, null]}]}}
```

Words are spelled for the MMS alphabet by `lyric_tokenize.normalize_for_mms` (numbers via `num2words`, other scripts via `uroman` when installed; Cyrillic and Greek look-alike letters inside Latin words read as Latin); an empty spelling means the word cannot be aligned. A line with `romaji` is aligned on its romaji words instead (uroman reads kanji with Mandarin readings), the span they were sung in is shared out over its characters (`romaji_onto_characters`), and it stays out of the song pass, whose words must match the line's. Each window is aligned as `* word … *` so the star token absorbs anything that is not the line. Version 2 runs the model on 20 s chunks with 2 s of context on each side, starting on a frame boundary (320 samples), and keeps each chunk's middle frames, since attention grows with the square of the length; the song pass is `skipped` when there are too few frames for the text or frames × tokens is too large, and `failed` when it raises. Stage events carry `phase` (emission, lines, song). `line_realign` keeps sending version 1 (a version 1 request with a saved emission also reports `emission`, with `cached: true`). Emission-only mode, which the cloud GPU runs after separation: `python -u -m backend.workers.ctc_align_worker --emission vocals.wav --out emission.npy --model-dir DIR [--allow-download 0|1] [--device auto|cpu|cuda]`; it ends with a `{"event": "done", "frames", "chunks", "device", "seconds"}` line. Exit codes match the RoFormer worker; a timeout (`ALIGNMENT_TIMEOUT_SEC`) or stall (`ALIGNMENT_STALL_SEC`) stops it.

**Single-line re-align** (`line_realign.py`, `POST …/realign-line`). The search window is the line ± `search_window` (default 1.5 s, at most 3 s), never past the neighbouring lines of the same voice. Candidate starts are the line's current start and every phrase start (singing after 0.12 s of quiet) in the window; each scores vocal coverage over the line's length, plus quiet just before it, minus distance moved. The end snaps to the nearest release (0.25 s of quiet). DSP word timing reads only the window's audio. When the neural aligner is ready and has a free slot, it searches the whole window too and wins if confident. The response is `{status: ok | not_found, line, engine, elapsed, fallback_reason, detail, window}`.

### 2.8 Mixing, subtitles and rendering

- **Mixer.** `audio_mixer.mix_and_shift` blends the guide vocal with `amix … normalize=0` plus `alimiter`, so the backing track keeps its level. A `MIX_QUALITY` context variable picks the pitch shifter: fast resampling for previews, Rubber Band (`pitchq=quality`, formants preserved on the guide vocal) for renders, with a fallback graph for older FFmpeg builds. `/mix` results are cached by file name while newer than the stems and made by the current mixer (`MIX_CACHE_VERSION` in `master_audio.py`, noted in `output/.mix-cache-version`; renders older than that note are made again). After each `/mix` (once its save succeeded), each re-separation, and once for every song at startup, `prune_mix_cache` keeps the song's `MIX_CACHE_PER_SONG` (default 6, 0 keeps all) most recently used mixes; see Master audio.
- **Vocal levels** (`services/vocal_mix.py`). A song's `vocal_levels` (`POST /mix`, `RenderRequest`, `render_settings`) say which vocals a mix keeps beyond the guide level: `backing` (needs the lead/backing parts), and the lead divided `by: "lines"` (`singer1`, `singer2`, `both`: the level of the lead during that singer's lyric lines) or `by: "voices"` (`male`, `female`: needs those parts). A key that is not set takes `guide_volume`; one whose stems are missing, singer levels on a song with one singer, and voice levels without the split are ignored, so levels survive parts being dropped and made again. `plan_mix` turns levels, lines and the stems on disk into a plan. When every vocal ends up at one level the plan has no key and `master_audio.make_master_mix` calls the mixer exactly as before (whole vocal stem at that level, the old file name). Otherwise `write_kept_vocals` sums each part at its gain into a temporary 32-bit float WAV (`<mix>.vocals.tmp_<hex>.wav`, a block at a time; mono repeated, short parts padded, differing sample rates refused), which the mixer blends in at level 1, so the final-quality pitch shift treats it as it treats the guide. The line gate (`gate_curve`) is a list of (time, gain) points: a line's level starts 0.15 s early and holds 1 s past its end into time no line covers, a `both` line or overlapping lines of two singers take `both`, the rest of the song takes the lowest level in use, and each change is a 50 ms ramp. A keyed mix is named `{track}_mix_<semitones>_<guide %>_<8 hex>.wav`; the hex hashes `VOCAL_MIX_VERSION`, each part's file name and gain, and the gate's points, so it follows line timing and not line text. `/mix`, the render (scratch name, never reused), re-separation and a finished vocal split all go through `make_master_mix`. Saving lines (`POST …/lyrics`, whose reply carries it) or storing re-timed ones sets `master_stale` on the song when its current master is no longer the mix its stored settings name (`master_audio.mark_master_stale`); the next `/mix` clears it, and the studio asks for that mix when it sees the mark.
- **Practice vocal** (`routers/practice.py`, `master_audio.make_practice_vocal`). Practice switches the original singer on and off without a new master: the browser plays the vocals by themselves beside the master. At the original key on a server that streams WAVs that is the vocal stem (`vocals_url`) and nothing is made. At another key the mixer runs with the stem as its only input, which is the chain the backing takes in a master at that key (the same pitch filter and limiter, so the same 5 ms limiter delay; `tests/practice/test_practice_vocal_in_step_with_master.py` checks the two come out sample for sample alike from one recording). The preview shifter (`asetrate`, `atempo`) places its splices by the sound, so a shifted vocal and its master still differ by about a hundredth of a second, as the guide vocal already does inside a shifted master. With `PREVIEW_AUDIO_FORMAT=aac` the vocal is made at the original key too and served as an `.m4a` like the master, since a WAV beside a compressed master would start early. The file is named as a mix with a vocal key of its own (`{track}_mix_<semitones>_100_<PRACTICE_VOCAL_KEY>.wav`), so the mix cache's rules cover it unchanged: reuse while newer than the stems, `MIX_CACHE_VERSION`, pruning with the song's other mixes (each practised key takes one of the `MIX_CACHE_PER_SONG` places), the startup prune and deletion with the song. The route checks free space only when a file must be made, is not paused by an update drain (it registers no job, like `/mix`), and is always the whole vocal stem: a master that keeps some vocals (`vocal_levels`) plays them twice with the practice vocal on.
- **Master audio** (`master_audio.py`). Mix file names, the mix cache, and the project's `master_audio_path` / `master_audio_url`. The path is always the WAV (exports, renders, the waveform). With `PREVIEW_AUDIO_FORMAT=aac` the URL points at an AAC copy (`AudioMixer.encode_preview`: 160 kbps, `+faststart` so playback and seeking start at once), re-encoded when the WAV is newer and served as `audio/mp4`; without an AAC encoder, or when encoding fails, the studio streams the WAV. A reused mix gets a new access time and keeps its modification time, so its `?v=` URL and its `.m4a` stay valid. `prune_mix_cache` (never raises) matches only `{track}_mix_<semitones>_<guide %>.wav` and its keyed form with `_<8 hex>` (a keyed mix is dated against the vocals and every part file beside them, which can delete one that was still good but never keeps a stale one) (never `.tmp_` files, which the startup sweep deletes instead, `{id}_master.wav` or other songs) and deletes each WAV with its `.m4a`: first the mixes that can never be served again (older than the marker, the instrumental, or the vocals when the guide is above 0), then, ordered by last use (the latest access or modification time of the WAV and its `.m4a`), those past the limit. Every song's current `master_audio_path` (compared by file name) and any mix used in the last 60 s are never deleted: such a mix takes a slot only when it is among the `MIX_CACHE_PER_SONG` most recently used, and is otherwise kept on top of the limit, so a song can hold more mixes than that. It copies the masters' names under `PROJECTS_LOCK`, releases it, then takes `_MIX_CACHE_LOCK` (which `reusable_mix_path` also holds while it checks and touches a mix), so the order is always `PROJECTS_LOCK`, then `_MIX_CACHE_LOCK`. The intake's first `{id}_master.wav` is not pruned. At startup `prune_mixes_of_every_song` runs it once per track in the library, on a daemon thread (`start_pruning_mixes_of_every_song`, which resolves the output folder before the thread starts); songs that share a track but not its stems (one has its own backing track) are pruned on the mixer version and the limit alone. It never raises either.
- **Song analysis** (`project_analysis.py`). The chord and vocal-range routes, the ASS and chord sheet exports and the render detect chords or the vocal range when a song has none yet; the intake pipelines, `POST …/chords/detect` and vocal-range re-analysis always do. `ensure_chords` / `ensure_vocal_range` detect outside `PROJECTS_LOCK` and store under it, keeping what was stored meanwhile (first writer wins) unless forced. One analysis of each kind runs per song at a time (`_analysis_lock`), so a backfill that arrives while the intake's analysis runs waits for it and returns its result. The intake's forced chord detection passes the progression it replaces (`replacing`) and keeps a chord edit saved while it ran. Chords come from the instrumental, else the original track. The melody (`services/melody.py`, `ensure_melody`, `GET …/melody`) is the vocal stem's pitch frame by frame: `VocalRangeAnalyzer.pitch_contour` keeps what the range analysis reads and throws away (both walk the same frames through `_frame_pitches`, 32 ms apart, so the range's numbers are unchanged), and `melody.clean_contour` makes it followable (a note of a quarter second or less that sits an octave from the notes on both sides is moved back, a pause of one or two frames inside a note is drawn through, a five-frame median evens the jitter, and a note under three frames is dropped). The detector follows one voice, so the lead part is read when the vocals have been split into lead and backing (`source: "lead"`), else the whole stem. Unlike the other analyses it is not stored on the song (7,500 numbers for a four-minute song would be rewritten with every save of `projects.json` and sent with every song): it is kept as `stems/<track>/melody.json` with its source's name, size and modification time, and is current only while those and `MELODY_VERSION` match, so new vocals, a split that came or went, or a restored file all make it again; the folder goes with the song. One melody is worked out at a time across the server (`_MELODY_SLOT`, since the analyzer reads the whole stem into memory), a kept one never waits for that, and it takes no job slot (`WORKER_SEMAPHORE`), which would hang the request behind a render. Vocals with nothing sung, or that cannot be read as audio, answer `detected: false` (the first is kept, the second is not). A song's key is its vocal analysis's estimate, else a top-level `estimated_key` (older songs). The YouTube kit (`youtube_package`) describes the key and the vocals kept (guide level and `vocal_levels`) of the last render (`render_settings`), else the song's current ones. Its chapters start at the first line and after every instrumental gap of 4 s or more (the countdown's rule, `ass_generator.instrumental_gaps`) and last at least 10 s (a closer section joins the chapter before); with fewer than 3 YouTube would show none, so the block is left out. Its title stays within 100 characters and its tags within 500. A blank or placeholder artist ("Unknown Artist") is left out of the title, the tags and the description, which then drops its "originally by" clause and Original Artist line.
- **Looks.** A video and the stage are drawn in one of five looks (`backend/assets/shared/stage_looks.json`, read by `services/stage_looks.py` and by the stage): Marquee (the default), KTV, Songbook, Cinema and Prompter. A look names a layout (`stack`: one reading place with the next line under it; `rows`: two rows taken in turn; `column`: a column that moves up), its colours, typefaces, motion, cover-art treatment and where everything sits in a 16:9 and a 9:16 frame. Lengths are in u, 1% of the frame's short side (10.8 px in a 1080p video); sizes are em sizes and vertical positions are baselines. The id of one of the nine presets the looks replaced still resolves to the look nearest it (`legacy_ids`).
- **One frame for the stage and the video.** Four rules are written once in Python and once in TypeScript, and both suites run the same case files (written by `python -m backend.tools.stage_cases`; a test fails when a file is stale): *when* things show (`stage_timing.plan_timeline` / `utils/stageTimeline.ts`, `stage_timeline_cases.json`), *how large* a line is and where its rows break (`text_fit.fit_block` / `utils/stageFit.ts`, `stage_fit_cases.json`), *where* a line goes (`stage_layout` / `utils/stageLayout.ts`, `stage_layout_cases.json`), and *what is drawn at a moment* (`stage_scene_cases.json`: a made-up song in every look and format at about 140 moments, read back from the subtitle files and reproduced by `utils/stageScene.ts`). Neither renderer measures or wraps text itself: both add up advance widths from `stage_font_metrics.json` (written from the bundled fonts by `python -m backend.tools.font_metrics`), so both break a line at the same word. Times round to the centisecond and lengths to a thousandth of a u, halves up, on both sides.
- **Subtitles.** `ass_generator.generate_ass_content` keeps its signature; `ass_style.resolve_look_style` decides the look, colours, size, format and cues from the arguments and the request's `style_config` (its docstring lists the rules), and `ass_look.generate_look_ass` writes the file. Nothing wraps (`WrapStyle: 2`): every row of a line is one event, placed by its baseline with `\\an7`..`\\an9` and `\\pos`, sized with `\\fs` (libass takes the font's cell height, so the em size is multiplied by the face's `ass_size`), coloured with `\\1c`/`\\2c`, and filled with `\\kf` on absolute centisecond boundaries with `\\k` spacers (line mode: `{\\k<lead>}{\\k0}`; a line without word timing fills like line mode). A `stack` line comes up into place with one `\\move` and `\\fade`; a `column` steps once per line, each visible row one event per step that moves and then holds, so a line's fill is never cut in two (a line takes the reading place before its first word). Each event's Name field says what it is (`lyric:3`, `next:4`, `sung:2`, `part:3`, `romaji:3`, `title`, `end`, `countin:5`, `break`, `progress`, `caret`); libass ignores it and the tests select by it. Every look draws an opening title card (first line at 6 s or later), a count-in over the last 3 s before a line that follows a gap of 4 s or more (numerals; dots in KTV), the seconds left of a break (at most its last ten minutes), the part's name where the singer changes (`part_names`), a progress line (a drawing under an animated `\\clip`) and an end card. Whatever starts with the song is solid from the first frame. Words in parentheses are ad-libs (smaller, fainter, italic where the look has an italic face) by the rule the stage uses (`lyric_tokenize.adlib_flags`); words are spaced as the line's text writes them; a line's `romaji` is a row of its own. The libass facts all this rests on are pinned on real frames by `tests/subtitles/test_libass_assumptions.py`. What a request may no longer set (`font_name`, `font_size`, `outline_*`, `shadow_*`, `margin_*`, `chord_alignment`) is ignored. A tab opened before the looks sends its preset's own colours with every request: with a legacy id those are not taken for a choice. The `.ass` download is the same file without the progress line; it names its fonts in a header comment because it is laid out for them. CJK glyphs outside KTV's own typeface come from `fonts-noto-cjk`, installed in the app image and in the Modal render image alike (a test keeps their font packages in step).
- **Video.** `render_worker` mixes at final quality into `{track}_final_audio.wav`, which it deletes when the render ends (finished, failed or cancelled), and renders 1080p60 (16:9 or 9:16) through FFmpeg with libass, using the bundled stage fonts (`backend/assets/fonts`, static cuts that libass finds by their legacy family names; see `backend/assets/README.md`) over the look's ground colour. The worker passes the look to the renderer: `look_backgrounds` gives each look its cover-art treatment (Marquee grey and dark, KTV blurred, Songbook a faint wash, Cinema sharp, Prompter nearly black), dims or washes an upload, and for Cinema sets every kind of picture into a 2.39:1 frame (a square in 9:16) with `pad`; with no look, and for KTV, every graph is what it was before the looks. `python -m backend.tools.look_frames --out <dir>` renders stills (and with `--clips` short videos) of every look through this same path. `video_renderer.prepare_background` feeds the filter graph at a genuine 60 fps for every backdrop (`-loop 1 -framerate 60` for stills, `fps=60` for looping videos, `r=60` for the colour source), so the sweep is drawn for each output frame; a still image (custom, or the song's thumbnail with its blur and darkening) is processed once into a PNG instead of per frame, falling back to the per-frame chain if that step fails. The background style (`style_config.background_style`, with `background_palette` and `background_tone`) picks what is drawn when there is no upload: the thumbnail still (default), the drift (the thumbnail processed once at 1.12× and panned by `crop`, decoded once through the `loop` filter), aurora (one-frame Gaussian orb sprites overlaid at song-time positions) or the spectrum (`showcqt` of the song, tinted from the palette), or the plain colour. Aurora and spectrum are drawn at a quarter of the output size from inline lavfi sources, add the stage's scrim and are upscaled, so cloud renders ship nothing extra for them. Their motion numbers live in `backend/assets/shared/background_motion.json`, which the stage imports too. The libx264 preset is `FFMPEG_PRESET` (default `veryfast`, CRF 18). Each aspect ratio has its own file, `{track}_karaoke.mp4` for 16:9 and `{track}_karaoke_vertical.mp4` for 9:16, so a render replaces only its own format's video. FFmpeg (or the cloud download, and the local render after a failed cloud one) writes `<name>.part.mp4` next to it, which `os.replace` moves into place only when the render succeeds; a failed or cancelled render removes the part file and keeps the previous video, and the `lifespan` hook deletes the part files and scratch mixes a restart left behind, including the mixer's unfinished `{track}_final_audio.tmp_*.wav` (`render_worker.remove_render_leftovers`). `video_url` is the latest render and `videos_by_aspect` maps each format to its latest file, which the Export dialog offers next to it. Each download is named after its format (`Artist - Title (16x9).mp4`, `(9x16)`; a video from before `videos_by_aspect` keeps the bare name), and after a failed or cancelled render the dialog offers the kept video of the format being rendered first, then the other format's.
- **Cloud export** (`remote_render.py`, `render` in `gpu/modal_app.py`). With `RENDER_REMOTE=modal`, `ffmpeg_args` builds the same command against upload names (`background.*`, `audio.*`, `subtitles.ass`, fonts in `/fonts`), and `modal_jobs.run_modal_job` spawns it on a 16-core CPU, streams FFmpeg's `-progress` lines back into the same `RenderProgress` parser and returns the MP4. Cancel stops the remote call; an unavailable service, no CPU within `RENDER_REMOTE_QUEUE_SEC` or a failed render falls back to the local render. `modal_jobs` is shared with the cloud GPU separation and cancels the remote call whenever following it raises, including from a progress callback; it reports the wait for a container every 5 s (shown as "Waiting for a cloud CPU… 45 s") and logs it once the job starts. Opening the Export dialog sends a beacon to `POST /api/render/warmup`, which spawns `render(warmup=True)` at most once a minute (`RENDER_REMOTE_PREWARM`); the container then waits `RENDER_REMOTE_SCALEDOWN_SEC` (120 s, separate from the GPU's 30 s) for the render.

## 3. Frontend

### 3.1 Design system

- **Look.** The app has one look, Marquee: black, an off-white ("bone") for text and rules, and one yellow ("bulb"). Six rules hold it together. *Yellow means lit*: the line being sung, the played part of the waveform, a control that is on, and the one action that moves a song forward on a screen (Search, Export, Render); nothing else is yellow. *Normal is quiet*: only exceptions get colour or a label, so a song that is ready carries no badge and a job that is running says nothing about the server until it has gone quiet. *Rules, not boxes*: a 2 px bone rule divides regions and a hairline divides rows; only controls (fields, buttons, menus, dialogs) have an outline, never one inside another. *Two voices*: condensed capitals (`.ks-display`, Sofia Sans Extra Condensed, never under 20 px) name things and actions; sentence-case Sofia Sans explains. The capitals come from CSS, so the text in the DOM, and with it every accessible name and test lookup, is sentence case. *Square and flat*: no radius, shadow, gradient, blur or glow outside the stage, which is the video. *One flourish*: the home headline is sung once on arrival.
- **Tokens.** One `:root` block in `index.css` holds the colours as `--theme-<name>` with `--theme-<name>-rgb` channels (bg, surface, surface-subtle, surface-raised, border, border-subtle, text, text-muted, text-inverse, accent, accent-hover, accent-text, sung, unsung, success, warning, danger, focus, overlay) and the font stacks (`--theme-font-display`, `-heading`, `-body`, `-mono`). Nothing in JavaScript sets or reads them and there is no `data-theme`. Tailwind maps `theme-*` colours to `rgb(var(--theme-<c>-rgb) / <alpha>)`. `border` is the edge of every field and control; `border-subtle` is for row hairlines only (too faint for a field). Monospace is kept for keycaps, pasted lyrics and raw error text; numbers elsewhere use the text face's tabular figures. The smallest text is 13 px.
- **Guards.** `tests/theme/flatLookGuard.test.ts` fails on a removed token or utility anywhere, and on gradients, blur, shadows, radii, tinted fills and sparkle icons outside the stage files. `tokenParity` keeps Tailwind, `:root`, `index.html` and the manifest on the same colours, `tokenContrast` checks the pairs in use, and `tests/copy/plainWordsGuard.test.ts` keeps "AI", "Smart" and engine chatter out of the wording.
- **Stage looks.** Five looks (`theme/stageLooks.ts`, a typed reader of `@shared/stage_looks.json`) set how the stage and the exported video are drawn; Marquee is the default (`DEFAULT_STAGE_LOOK_ID`). They are the only themes there are. The stage files (`components/stage/*`, `LyricDisplay.tsx`, `ChordBar.tsx`) are outside the flat-look rules, because the stage is the video; inside the frame only what libass can draw is used (flat fills, an outline, one soft shadow, opacity, straight moves).
- **Primitives** (`components/ui`): Button, IconButton, Panel, SegmentedControl, Tabs, Dialog (with header, body and footer), Menu, Slider, Switch, Checkbox, Badge, Field, Kbd, Spinner, ProgressBar / ProgressRing, Skeleton, EmptyState, VisuallyHidden. Interactive primitives keep 44 px touch targets and tighten from `md:` up. Dialogs render only while open, put the close button first, trap focus and close on backdrop click unless they are gates (sign-in). `utils/cn.ts` merges classes with the custom token classes registered. A primary Button is a solid yellow block and a secondary one an outline; Panel is a titled section under a rule, with no box; Tabs and SegmentedControl are text with the chosen one underlined; Badge is coloured text (warning and danger always with an icon), never a pill.

### 3.2 Studio layout

- `App` wraps `AppContent` in the palette provider. `AppContent` shows the library (`TrackSearch`), the `ProcessingView`, or the `StudioWorkspace`.
- **Header** (`StudioHeader`): the wordmark, New Song, the palette trigger, a render in progress (as text), help, the profile and the single Export button, a yellow block; on the library screen also an **Install** button while the browser can install the app (§3.7).
- **Workspace** (`studio/StudioWorkspace.tsx`): on desktop a grid of the main column (song header, stage and timeline) and the inspector aside (Audio Mix and Stage Look panels); on phones three tabs (Stage, Timeline, Mix & Look). The song header sets the title in marquee capitals over the sync note (fidelity, mean confidence, auto-aligned) and the stems note as plain text, and the check-up button, which counts what `utils/songCheckup` says to fix and opens the song check-up. Above the stage a first-time user sees the first-song card (see Guidance below).
- **Practice** (`hooks/usePractice`, `components/practice/PracticePanel`): the song header's Practice button (or P, or `?practice=1` beside `?project=`, written with `replaceState` so Back still returns to the library) swaps the timeline for the practice panel. `App` calls `usePractice` whether or not practice is on and hands the panel to `LyricTimelineEditor` as a node (`practicePanel`), which renders it after the stage and hides its timeline panel with both the `hidden` attribute and the `hidden` class: the editor is never remounted, so unsaved lyric edits wait behind the panel. The stage and the inspector stay. On phones the panel sits under the stage on the Stage tab, and opening the Timeline tab leaves practice (`App.selectWorkspaceTab`), as do a tour and any guide step that goes to the timeline. Repeating a part: `utils/practiceSections.practiceParts` splits the lines where `planTimeline` marks a pause (`LineTiming.gap`) and cuts a run of more than eight lines at its longest inner pause; `utils/practiceLoop` is the rule (each pass starts 2 s before the stretch and turns 0.6 s after it, never in the song's last 0.3 s, and playback more than 2 s past the turn is left alone); `hooks/usePracticeLoop` watches the playback clock, aims the turn with a timer between its four ticks a second, and in `part` mode moves the stretch to the part the listener seeks to (a stretch picked by lines stays put). The dock marks the stretch on the scrubber (`WaveformScrubber`'s `range`). The original singer (`hooks/useOriginalVocal`): a second audio element, made with `new Audio()` and never put in the page (the dock's stays the only `<audio>`), plays the song's vocals alone from the address `POST …/practice-vocal` gives for the master's applied key (§2.8), asked when practice opens (on the first switch-on for a browser saving data) and again when the key changes. Its sound runs through the studio's audio graph (a media-element source into a gain node into the studio's analyser), so the switch is a 15 ms fade of the gain and nothing reloads; without a graph the element's own volume and mute carry the level. It takes the master's volume and mute, and `utils/vocalFollow.followMaster` keeps it with the master on the master's play, pause, seek and speed events and four times a second between them (each tick also looks for the dock's element and starts listening to it, because the dock's code can load after practice has opened from a link): within 20 ms it is left alone, up to 250 ms it plays 3% faster or slower until the gap is under 8 ms, and beyond that it jumps, aiming ahead by a lead that grows or shrinks when a jump lands off. The element is first started inside the click that switches the singer on (browsers that only let a clicked element play), keeps running silently while switched off so the next switch is immediate, and is stopped and emptied when practice is left. A guide vocal already in the master cannot be switched off this way: the panel shows what the mix holds and a button that asks for the mix at guide 0 (`mix.commitGuideVolume(0)`); practice never changes the saved mix by itself.
- **Transport** (`transport/TransportDock.tsx`): the only `<audio>` element (it never remounts), waveform scrubber, play, time, speed, key stepper and volume; fixed at the bottom on phones. It publishes `--dock-height` so toasts sit above it.
- **Safe areas.** `index.html` uses `viewport-fit=cover`, so the installed app draws under the status bar and notch: the header pads `env(safe-area-inset-top)`, the app shell and the fixed phone dock pad the left and right insets (landscape), and the dock, sheets and the palette pad the bottom inset.

| `useServerUpdatePrompt` | where the server reports `self_update`, offers an Update now toast when GitHub's `main` is ahead of the running build (`GET /api/health?check_remote=1` on load, when the tab becomes visible at most every 2 minutes, and every 10 minutes); the button posts `{"action": "update"}` to `/api/system/update`, and `useUpdatePrompt` then offers the reload |

**Timeline tools.** The offset, replace-lyrics and duet dialogs mount from `timeline/TimelineDialogs` with one "which dialog is open" state. Above the lines, `timeline/UncoveredVocalsNotice` lists the vocals without lyrics, worked out live from the sync report's `vocal_regions` and the current lines (`utils/uncoveredVocals.ts`, the backend's `uncovered_vocals` rule), and a click plays each stretch; lines the server added as repeats carry an "Added repeat" chip. The Re-import dialog marks the listing in use and shows each listing's quality flags.

**Hand edits.** The editor routes hand edits through a setter that compares each line's content (text, times, words) with the previous state: changed lines become `align_method: "manual"` and lose their confidence, and a line edited back to its saved content gets its saved metadata back (`utils/manualEdits.ts`). Aligner results, undo/redo and server updates bypass it. Whole-song re-alignments and re-made stems started from the studio send `keep_manual`, so these lines keep their timing (`lyric_sync.prepare_existing_lines`), except lines of two or more words that the editor only spread evenly (`wordsSpreadEvenly`, the same rule as the backend's `words_spread_evenly`; `backend/assets/shared/word_spread_cases.json` pins both). Retyping such a line spreads its words again even when the word count stays the same.

### 3.4 Command palette

`commandPalette/` holds a registry: components register commands (`useRegisterCommands(scope, commands)`) and searchable sources (songs, lyric lines) while mounted, and the palette reads them when it opens. <kbd>Ctrl</kbd>/<kbd>⌘</kbd>+<kbd>K</kbd> toggles it unless another dialog or the sign-in gate is open. Ranking puts prefix matches first, then word starts, substrings and loose subsequences; results are capped at 50 and recent commands are kept in `karaoke_palette_recent`. Studio commands cover playback, stage, mix (including "Improve stem separation…"), themes, navigation, song actions, and the timeline's lyric tools (save, undo, tap-to-sync, re-align the selected line or all lines, cancel a re-alignment). The context's `runCommand(id)` runs the command a mounted component offers under that id and returns whether there was one; guidance uses it to open the lyric tools, whose dialogs live inside the timeline editor (`lyrics-replace`, `lyrics-offset`, `lyrics-duet`, `lyrics-realign-all`, `lyrics-review-show`, `stems-improve`). The review filter has one id per direction (`lyrics-review-show`, `lyrics-review-all`) so running it by id always means the same thing. The guide adds `guide-tour` and `help-features`, and a `features` source beside `songs` and `lyric-lines` (sources list nothing until a query is typed).

### 3.5 Stage

`LyricDisplay` is the stage's shell: the toolbar (`StageToolbar`, a row above the frame, an overlay in fullscreen), the screen (`stage-screen`, the video's shape inline), the chord bar over it and `StageFloatingControls` for fullscreen. The screen holds `stage/StageFrame`, a box of the video's shape centred in whatever space it gets, with `--u` (1% of its short side, `1cqmin`, set on a child because a container's own container units resolve against its parent) the unit everything inside is placed in. `utils/stageScene.planStage` places a song's lines once per song and style; `sceneAt(plan, t)` gives every piece of text and every shape on stage at a time, and `StageFrame` draws them: each row hangs from a 1.5 em strut, which puts its baseline where the scene says whatever the typeface's metrics are, and is placed by custom properties (`--x`, `--y`, `--size`, `--alpha`). Motion is a function of the song time, never a CSS transition, so a paused or scrubbed stage is the video's frame at that moment. The line a singer follows has a control per word (named as the lyrics spell it, with the stable `word-sung-<n>` fill spans); any other line is one control that seeks to its start. `StageBackground` draws only what the export draws: the look's ground, then the cover art (the export's own still for the look, from `GET /api/project/{id}/backdrop?look=…`, panned for the drift), aurora orbs, the spectrum (`StageSpectrum`, a canvas fed by its own analyser and calibrated against `showcqt`), or an upload with the look's dim or wash (the song's loop, `project.song_loop`, is drawn as an uploaded video when the background style is `loop`; `StudioWorkspace` hands it over, and a song without one shows its cover art); aurora and spectrum add the export's scrim, and a look that frames its picture (Cinema) draws all of it inside that frame. Drift and aurora positions are functions of the song time (`theme/stageBackgrounds.ts`); they hold still under reduced motion. Known differences from the video: CJK glyph shapes outside KTV (a system font here, Noto CJK there, at the same widths), kerning (both size text without it and draw with it), and the chord bar, visualizer and spectrum, which are live controls here (the visualizer is the stage's own drawing, kept to the band the video draws its bars in, under the lyrics, in the same colour). The Look panel (`VisualThemePicker`) lists the looks as rows with a sample each (`stage/LookSample`: the same renderer with nothing to press, showing a strip of the frame, its whole width and the band of its height the words are in, so every look's type can be read). The stage's size comes from a height budget (`.ks-stage-fit`, `--stage-h`) that covers the toolbar row and the frame; on a phone a 9:16 frame is as wide as lets all of it sit above the transport dock.

**The stage window.** `/?stage=1` is the stage alone in a window of its own, for a second screen: a TV shows the lyrics while the studio's window keeps the timeline, the mix and the one `<audio>` element. `main.tsx` mounts `components/stage-window/StageWindow` for that address in place of `App`, which would sign in, poll, offer updates and save stage settings from a window that only shows what it is sent. The two windows are pages of one origin in one browser and talk over a `BroadcastChannel` (`utils/stageLink.ts`); nothing goes through the server, and a stage on another device would need another carrier for the same messages.

- The studio's stage (`LyricDisplay`, through `useStageLeader`) sends `state`, everything it draws apart from the song position (the lines as edited, saved or not, the look, colours, size, background, chords), when it changes and when a stage window says `hello`. It sends `transport` (`{time, at, isPlaying, rate, seek}`; `at` is `Date.now()`, since `performance.now()` starts from a different moment in each window) whenever the playback clock publishes (the player's `timeupdate`, a seek) and when play, pause or the speed changes. Unmounting (the song closed) and `pagehide` send a null `state`.
- The stage window keeps time by itself between those: its own `PlaybackClock` has a live reader that works the position out from the last `transport` (`transportTime`), stopping after `MAX_COAST_SEC` of silence, since a player that reports four times a second and goes quiet has stalled. `useInterpolatedTime` follows a live position given without an audio element for this; before, it stopped 350 ms after its last update.
- It draws `LyricDisplay` with `bare`: the screen alone, filling the window, with no toolbar, no floating controls and no palette command or shortcuts of its own. `StageWindow` has the keys: Space and the arrows post `command`s (`play` and `pause` by name, never a toggle, and addressed to the studio it follows, so two studio tabs or a press made in both windows cannot undo each other), and F fills the screen, which a browser only allows from a gesture made in that window, so a prompt asks for one.
- It never mounts `useVisualTheme`: the look, colours and lines are the studio's, so two windows cannot overwrite each other's stage settings.
- `utils/stageWindowOpen.ts` opens it as a named popup and, where the browser has the Window Management API and the user allows it (Chromium over HTTPS), moves it onto the other screen. The toolbar button (from tablet width up) and the palette's "Open the stage window" bring an open one forward instead of reloading it.
- The spectrum background needs the player's analyser, which only the studio's window has, so a stage window shows cover art for that style; the visualizer bars draw their own beat without one.
- Tests run on an in-memory `BroadcastChannel` (`tests/helpers/fakeBroadcastChannel.ts`, installed in `tests/setup.ts`): Node's own would deliver between tests.

**A show.** `/?show=1` is the host screen of a karaoke night: one computer drives two screens, the host's (`components/show/ShowScreen`: who is on, the queue, adding a singer) and the room's (a stage window on the TV). `main.tsx` mounts `show/ShowApp` for that address in place of `App`: its own sign-in (`hooks/useShowAuth`, `show/ShowSignIn`), then the screen; there is no library to edit and no song open. The sign-in takes the studio passphrase or, where the server has one, the show passphrase (§2.1), tried in that order's reverse: the show's first, since it is the one a venue's host has. A show sign-in has no "Back to the songs" (`ShowScreen`'s `canLeave`), and in a browser that holds only a show token the app's plain address is the host screen too. "Run a show" on the home screen and in the palette goes there (`utils/stageWindowOpen.openShow`).

- **The queue** (`utils/showQueue.ts`) is a pure reducer over entries `{id, singer, source, status}`. A source is a library song (`projectId`) or a YouTube video (`videoId`); a status is `waiting`, `playing` (one at most), `done` or `skipped`. It is kept in `localStorage` (`karaoke_show_queue_v1`, the night's name in `karaoke_show_title_v1`); an entry that was on stage when the page went comes back waiting at the head of the line, since the song stopped with the page. A song joins the line where `turnPlace` has it when the action says `turns` (`add`, and `again` for a singer who has been on), else at the end. `turnPlace` reads the line as rounds: an entry's round is how many of its singer's songs are ahead of it, the one on stage included, and a joining song goes behind the last entry of its own round or an earlier one. Singers are told apart by name, capitals and spacing aside. Rounds are read from the line as it stands and nothing is stored about them, so the rule never moves an entry that is waiting, a move by the host stays, and with nobody on stage the head of the line (whom the stage window has called) is never passed. Whether singers take turns is the host screen's switch, kept in `karaoke_show_turns_v1` (on unless saved as `off`); `ShowScreen` sends it with each action and, with `joinPlace`, says in the toast where the singer went. A waiting entry moves one place (`move`, the row's arrows) or to any place among the waiting ones (`place`, a dropped row). `show/ShowQueueList` drags its rows with `hooks/useReorderDrag`: pointer events and no library, so a mouse and a touchscreen both work. The rows are measured once at the press; the dragged row follows the pointer by a transform, clamped to the list, and passes a neighbour when its leading edge crosses the neighbour's middle (`dropIndex`), the passed rows shifting by its height and the row numbers showing the order a drop would give. The list itself is reordered only at the drop. A mouse or pen picks a row up anywhere but its buttons, a finger only by the grip (`data-drag-handle`, `touch-action: none`), so a finger on the row still scrolls the page. The page scrolls while the pointer is held near the window's top or bottom. Escape, `pointercancel`, a blurred window and a queue that changes under the drag (a song ending calls the next singer) put the row back.
- **Adding a singer** (`show/ShowAddSinger`): the name, then the song from two tabs. Karaoke videos searches YouTube through `POST /api/search` with "karaoke" added to the words (`utils/youtube.karaokeQuery`); a pasted YouTube link is taken as the video itself (`youtubeVideoId`) and titled by `GET /api/show/videos/{id}`. Library lists the ready songs of `GET /api/projects?scope=all&summary=1`.
- **A song that cannot be found** (`utils/songRequests`, `hooks/useSongRequests`). Once the song has been looked for (a video search has answered, or the library has no match for the words), Add a singer offers to request it: the typed words, the singer's name when one is typed and the name of the night go to `POST /api/show/requests`. It is offered beside video results too, since YouTube lists something for nearly any words, and never for a pasted link. The host screen lists what the server holds (`show/ShowRequests`, read-only). The studio's home screen lists the same requests above the setlist (`track-search/SongRequests`, nothing while the list is empty): "Find it" puts a request's words in the song search, a song started from that search while the words are unchanged removes the request (`TrackSearch.createFromResult`), and each row can be removed without making it.
- **The player** (`hooks/useShowPlayer`) puts the entry on stage whatever it is. A library song is fetched in full and plays in the host's window (`useStudioAudio` and the screen's one `<audio>`), with its lyrics stage drawn there by `LyricDisplay`, which is the leader the stage window follows as in the studio (the stage inputs a song gives, `hooks/useProjectStageInputs`, are shared with `StudioWorkspace`). A video plays in the stage window: there is one sound, and it is the window the room watches. The host screen shows it too, silently (the host's picture of a video, below).
- **Scenes** (`hooks/useShowStage`, `StageScene` in `utils/stageLink.ts`). The host sends what the stage window shows around the songs: `upnext` (the singer called), `idle` (the night's name), `lyrics` (the stage it is sent), `youtube` (`components/stage-window/StageVideo.YouTubeVideo`: YouTube's IFrame Player API, loaded by `utils/youtube.loadYouTubeApi` only when a video is first played, in the stage window and on the host screen that shows it too; the one script this app takes from another site) or `file` (`FileVideo`, a `<video>` of the server's copy). A video's player takes `player` commands from its host and sends back `report`s (`loading`, `playing`, `paused`, `ended`, `blocked`, `error`, with position and length about four times a second); each carries the scene's `play` number, so one playing's reports are not taken for the next's. A scene is sent again when a stage window says `hello`, and a null one when the host screen closes.
- **The host's picture of a video** (`show/ShowStageMonitor`, `utils/stageMonitor.ts`). Under "Now singing" the host screen plays the stage window's video once more, without sound: YouTube's player again (`mute: 1`, no controls) or a muted `<video>` of the same copy. It is a second playing, not the stage window's pixels (a page cannot read another window's YouTube frame), so it is kept in step from the reports: `followStage` takes where the stage's video is (`useShowPlayer`'s `isPlaying` and `videoTime`, stamped when heard) and where the monitor's is, and answers play, pause or a jump. It jumps at once for a seek (more than 3 s apart), and for drift over 0.75 s once the last jump has had 3 s to settle; a jump aims a little ahead of the stage, further when the last one still landed behind (loading took longer), 2 s at most. A stage that says it is playing and has not been heard for 2 s is taken as stalled, checked once a second. The monitor exists only while a `youtube` or `file` scene is on a stage window that is open, is remounted for each playing, and is `inert`: it takes no clicks or keys and is not read out. Nothing depends on it: when its player fails it says the video could not be shown there, and the stage's playing is untouched. It is never unmuted and never sent the host's volume.
- **A video YouTube will not embed** (`useShowVideos`, `useShowPlayer.videoMode`). Each queued video is asked about once (`GET /api/show/videos/{id}`); one that cannot be embedded is fetched at once, and followed every two seconds while it is. On stage it is `embed`, `file` (the copy is ready), `copy` (wait on the singer's card until it is) or `failed`. YouTube's player errors 101, 150 and 153 while playing mean the same thing found late: the video is marked, its copy fetched, and it starts from the copy when that is ready. Error 100 says the video is gone.
- **Sound needs a gesture.** A browser starts sound only in a window that has been clicked or typed in. A video that has not started four seconds after it was ready is reported as `blocked`, and the host is told to click the stage window once (the prompt to fill the screen is that click).
- YouTube refuses music in its embedded player on a page served from `localhost` or an IP address (error 150 for every karaoke video and for official music videos, while other videos play), so in development every karaoke video takes the copy path; embedding has to be tried on a real domain.

### 3.6 First load and the home screen

- **Boot shell.** `index.html` carries a small inline stylesheet and, inside `#root`, the top bar and a quiet outline of the page, so something paints as soon as the HTML and stylesheet arrive; React replaces it on mount. The shell's brand name is set in the display face, which starts that font file downloading while the script is still loading.
- **Fonts** are self-hosted, in three stylesheets written by `scripts/generate-fonts-css.mjs` (`npm run fonts`) from the `@fontsource` packages, whose own CSS names the variable families "Sofia Sans Variable" while the stacks say "Sofia Sans": `src/fonts.css` (the interface's faces, which Marquee uses too; loaded with the first screen), `src/stageFonts.css` (the other looks' faces, imported by `stage/StageFrame` and so loaded with the studio) and `src/stageFonts.ktv.css` (the 118 Japanese slices of KTV's face, imported on demand when that look is on). Vite hashes the files into `/assets`, so they are cached for a year. Each file is fetched only when text in its family and unicode range is shown. Each stage face must be the cut the backend bundles, whose widths both sides measure with. `selfHostedFonts.test.ts` checks that the declared faces match the ones the app and the looks name and that the page loads nothing from another site.
- **Deferred screens** (`deferredScreens.ts`). The studio workspace, transport dock, export, stem and song check-up dialogs (one chunk, `components/studio/studioBundle.ts`), the help dialog, the command palette and the guided tour (`components/guide/GuideTour`) are split out of the first-load script. `main.tsx` fetches them once the page is idle; a screen whose chunk has arrived renders synchronously like a normal import, and one still on its way suspends (`StudioSkeleton` for the studio, nothing for dialogs). A failed fetch is retried once; a screen shown again a second or more after its chunk failed fetches it again, so a dropped connection does not leave Help or the palette closed until a reload. If the studio's chunk is still missing (an update replaced the build while the page was open), opening a song reloads the page once (`reloadForMissingChunk`, at most once a minute, recorded in `sessionStorage`); the help and palette chunks never reload, since they open over a studio that may hold unsaved edits. Tests that assert on those screens synchronously call `loadDeferredScreens()` in a `beforeAll`.
- **Home screen** (`TrackSearch`). The intake box starts a link to a supported site (a download or a lookup site) at once (`utils/mediaLinks.linkSite`, the backend's host rule over the same `media_sites.json`, both suites running its `host_cases`) and answers a link to any other site with the sites that work (`UNSUPPORTED_LINK_MESSAGE`). Anything else is search words (`useSongSearch.isSearchable`: two characters or more, one in a script outside ASCII): `useSongSearch` sends them to `POST /api/search/songs` 350 ms after the typing stops, or at once on Enter or **Search**, with an `AbortController` per search so only the latest words' answer is shown, and never repeats a search for the same words. `track-search/SongSearchResults` lists the songs under the box: artwork that plays the song's 30-second preview (`useSongPreview`: one clip at a time from an `Audio` object that is never put in the page, since the transport owns the only `<audio>` element; a clip that will not play can be tried again, and being stopped mid-load is not a failure), title, artist, album, year and length (the length is never truncated: it tells versions apart), badges for what kind of recording it is (`versions`) and for explicit lyrics, and **Create Karaoke**, which starts the result's `url` through the same `onSelectTrack` a pasted link uses. A result that carries `project_id` is already in the library: it shows "In your library" or "Being made" and **Open**, which hands the app a card-sized entry to fetch in full. Five songs are listed and the rest on "Show more"; a status line (`role="status"`) says how many songs were found and, when the words were respelled, for which spelling. Under the songs, **Search YouTube uploads** lists `POST /api/search` results for the (respelled) words, for another recording or a song the catalogs do not have; a submit that finds no song searches them by itself. When a response has an empty `sources` (no catalog configured or reachable), typing stops searching, the status says to press Search, and Search lists the YouTube uploads as the results. Arrow keys move from the box into the results and between them, Escape returns to the box and, there, dismisses the results; dismissed results stay dismissed until the words change. The page opens on `track-search/SungHeadline`: the headline is swept from bone to yellow once per page load, word by word (a CSS animation; under reduced motion it stands still, already yellow), on two lines for a first visit and one compact line for a returning visitor. Visitors with no songs of their own also get three "how it works" steps, and the library opens on the Community tab when it has songs and theirs is empty. `karaoke_has_songs` in localStorage remembers a returning visitor so their page does not jump, and hides the pitch on phones for them.
- **Setlist** (`track-search/ProjectLibrary`) loads `GET /api/projects?summary=1` and lists the songs as numbered rows. A song's number is the order it was made in, so sorting and filtering do not renumber, and a ready song shows only its length; one being made, failed, cancelled or an album says so. Opening a row fetches the whole song (`App.openLibraryProject`), with a spinner on the row meanwhile; the command palette's lyric search still loads the full list when it opens.
- **Processing.** `ProcessingTips` shows one tip at a time while a song is processed (auto-advancing until the viewer presses Next tip), and `ProcessingExpectations` says under it what to expect: how long, that the page can be left, and that an automatic result sometimes needs a fix. The failed screen explains `project.error` in plain words (`utils/processingErrors.explainProcessingError`: the first matching rule of a short list, else a general answer) and keeps the raw message under "Technical details". **Try again** (and **Start again** on the cancelled screen) posts the song's link (`url`, kept from the start; `utils/processingErrors.retryInput`), else its `track_id` for songs from before links were kept, to `/api/process` with `retry: true`, which replaces a failed song and makes it with the lyrics pasted for it the first time (`services/intake_lyrics.py`); a song from an upload (`local_` id) asks for the file again instead, and a song picked from an album (`album_track`) is started again through `POST …/album/songs`.
- **Whole albums** (`album/AlbumTrackPicker`, `album/AlbumTrackRow`, `hooks/useAlbumListing`, `utils/albumTracks`). `App` shows the picker for a project at status `album`, in place of the processing screen. It fetches `GET …/album`, says where the song list came from, and lists the songs with their place in the album: a checkbox for each song not made yet, **Open** for a song made or being made, a name field for a picked song with a stand-in name (and **Rename** for any picked song), the album artist as an editable field, **Pick all**, **Make N songs** (`useTrackIntake.handleAlbumSongs`, which opens the first song's progress and says the others are in the library) and **Make it all one song** when `whole_allowed` (`handleAlbumWhole`). The library card of an album carries an **Album** badge and opens the picker again.
- **Guidance.** The first four pieces below tell a new user what to do and what to fix, driven by `GuideAction`s that `useGuideActions` carries out; the last, the guide, points at the screen itself:
  - *First-song card* (`studio/FirstSongCard`): four steps above the stage (play, check lyrics, set your key, make a video), each a button, and "Show me around", which starts the tour. A plain `<section>`, never a dialog, so shortcuts keep working. Shown until hidden (`useFirstSongGuide`).
  - *Song check-up* (`utils/songCheckup` + `studio/SongCheckupDialog`): rows of `fix`, `tip` or `ok` read from what the project already stores: no lines or `lyric_source: "none"`, the timeline's review checks (`collectLineIssues`), `sync_report.mean_confidence` under the low threshold, `uncoveredVocals`, a DSP `fallback_reason`, `separation.fallback_reason` and `requested`, Fast stems when a better preset is available (`useCapabilities`), and `sync_job` / `separation_job` in `error`. `checkupFixCount` (the `fix` rows) is the number in the header and on the card.
  - *Help* (`HelpModal`): "What you can do" (`help/HelpFeatures`) lists `utils/features.FEATURES` by group, the usage guide opens with the first-song steps, and the "Fix a problem" tab lists `utils/troubleshooting.PROBLEMS` (symptom, cause, steps, actions), with buttons only while a finished song is open. `App` keeps the tab to open (`helpTab`): guidance opens "Fix a problem", the <kbd>?</kbd> key and the header button open the shortcuts. The README's "When results are off" table repeats the list by hand.
  - *Export* (`ExportModal`): before a song's first render, `export/ExportNextSteps` lists render, download and upload; while one runs, a line says the dialog can be closed. After a render, `export/ExportYouTubeKit` ("Upload to YouTube", directly under the video) is five steps around the server's `youtube_package`: start the upload, paste the title, description and tags (copy buttons), and what to check before publishing. It reads whether the description has chapters from its timestamp lines, and says when a 9:16 video becomes a Short (`SHORTS_MAX_SECONDS`, from the rendered format and `project.duration`). Nothing is uploaded from the app.
  - *The guide* (`components/guide`, a deferred chunk): a tour of the studio (11 stops, one fewer on desktop, where the phone's tab bar is not shown) or of the home screen (5), and "Show me" for one feature. `App` holds only what was asked for (`guide: GuideRequest | null`, a tour or a feature id); `GuideTour` does the rest. For each stop it selects the phone tab the control is on, presses the button that uncovers a collapsed control (`open`, the transport's speed and volume), finds the control by its `data-guide` name (`utils/guideAnchors`: the copy that is shown, and of several lyric lines the one in view), scrolls it clear of the bars that are held over the page at that moment, and measures the part of it that can be seen. `GuidePointer` draws four flat rectangles around that box, a 2 px ring 4 px off it, and a callout placed by `utils/guidePlacement` (under the control, else over or beside it; a band across the edge away from the control below 640 px). A stop whose control is not on the screen is passed over. The words are data: `utils/guideStops` (stops with a title, a body and, for toolbars of icon-only buttons, a legend) and `utils/features` (the features of Help's "What you can do" tab, each with the sentence said while its control is pointed at). A tour is a dialog (`aria-modal`, focus trap, Escape, arrow keys; the control under the ring cannot be pressed; the page does not scroll; a playing song is paused first, since Space is off) and so is only ever opened when asked for: "Show me around" on the first-song card and under "How it works", Help's "Start the tour", the palette. One pointed-at control is a `role="group"` note instead: the control is pressed through the hole, which ends the pointing, as do "Got it", Escape, a press on the dim, focus moving on, or the control scrolling away; the shortcuts stay on. Help lists a feature's "Show me" only on the screen it belongs to, and a control this song or server does not render (vocal splits, the song loop, "Needs review" with nothing to review) says why in place of the button. `tests/guide/guideAnchorsInApp.test.tsx` renders the studio and the home screen and fails when a stop or feature names a control that is not there.
  First-run UI renders in every App-level test, because the test setup clears storage: its controls need names no other studio control has (`studioAccessibleNameUniqueness.test.tsx`), and it must not use `role="dialog"`, which would turn the keyboard shortcuts off (`isModalActive`).

### 3.7 Installable app

- **Manifest** (`public/manifest.json`): `id` `/`, standalone display, separate `any` icons and `maskable` icons (both a full yellow square; the maskable K sits inside the safe zone), a narrow and a wide screenshot for Android's install sheet, and a `share_target` that opens `/?title=…&text=…&url=…`. `utils/sharedLink` turns a share into the search box text (the first link to a supported song site, `utils/mediaLinks.linkSite`, else the shared words); `App` passes it to `TrackSearch` as `initialQuery` and strips the parameters from the address. A share never starts processing by itself. Its colours equal the `:root` tokens (`tokenParity.test.ts`).
- **App shortcuts** (`shortcuts` in the manifest, `utils/appShortcut`): the icon menu (long-press on Android, right-click in a taskbar or dock) offers "New song", "Upload audio" and "Continue last song", each opening `/?shortcut=new|upload|resume`. `App` reads it once: `new` focuses the song search and `upload` opens the upload tab (`TrackSearch`'s `focusSearch` and `initialMode`), `resume` opens the song stored in `karaoke_last_project` (written whenever a song opens, forgotten when the server answers 404), then the parameter leaves the address. `?project=` wins over a shortcut, and a shortcut never starts processing. Each has 96 and 192 px icons in `public/shortcuts/`, rendered from the SVGs beside them.
- **System bar colours.** The status bar follows `meta[name="theme-color"]`. The strip under Android's gesture pill is different: Chrome (153 and newer) paints it from the installed app's *manifest* `theme_color`, as it does the splash screen from `background_color`, and does not let a standalone app draw there (its edge-to-edge mode for installed apps, `WebAppShortEdgesCutoutMode`, is off by default). All three are the app's black, written once in `index.html` and `public/manifest.json`, so nothing recolours them at run time. An app installed before 2.13 under another theme may still ask for `/manifest.json?bg=<hex>`; the static mount ignores the query and serves the built file (`test_http_delivery.py`), and Chrome picks the new colours up at its next manifest check (about once a day, applied while the app is closed). Older Chrome leaves the strip black or white, which no page can change.
- **See-through system bars.** With `viewport-fit=cover` and `black-translucent`, an iOS home-screen app draws under the status bar and the home indicator. Chrome on Android does the same for an installed app only with `chrome://flags/#web-app-short-edges-cutout-mode` set to "Enabled (Standalone also enabled)"; by default it pads the page and paints the bars itself (above). The app is laid out for both: the header, the boot shell's bar, the phone dock, bottom sheets, the toasts and the end of the library page each add the matching `env(safe-area-inset-*)`, which is 0 where the bars are painted for it.
- **Service worker** (`public/sw.js`, registered by `utils/serviceWorker` in production builds only). Page loads go to the network and fall back to the precached `offline.html` ("Can't reach your studio", reloads itself on `online`); hashed `/assets/*` are cache-first, capped at 60 entries. It never handles `/api`, `/static`, non-GET or cross-origin requests and never serves the page from cache, so audio, projects and `useUpdatePrompt` always see the server. Changing what it precaches means bumping its cache names (`karaoke-shell-v2`, `karaoke-assets-v1`); `activate` deletes the others.
- **Standalone CSS** (`index.css`, `@media (display-mode: standalone)`): `overscroll-behavior-y: none` on `html` only, which governs the viewport and pull-to-refresh. `html` and `body` both set `overflow-x: hidden`, which makes `body` a scroll container that never scrolls; `none` or `contain` on it stops touch scrolls from chaining to the page, so nothing moves on a phone (`standaloneScrollGuard.test.ts`). On phones the transport dock is a solid band in the page background, the colour of the strip under the gesture pill, so dock and strip read as one surface (`installedDockEdge.test.ts`).
- **Icons and screenshots** are committed PNGs in `frontend/public` (exempt from the PNG ignore rule): the icons are rendered from `icon.svg` and `icon-maskable.svg` (a yellow square with a black K, the display face's own glyph drawn as a path), `apple-touch-icon.png` from `icon.svg` (iOS rounds it itself), and the screenshots from a `seed_demo` library. `pwaManifestInstall.test.ts` checks that each file has the size and colour type the manifest states.

## 4. Testing

- **Backend** (`pytest`). `tests/conftest.py` gives every test an isolated data folder and a hermetic ML setup: `SEPARATION_QUALITY=fast`, `ALIGNMENT_ENGINE=dsp`, downloads off, model folders under the test's temp directory, `HF_HUB_OFFLINE=1`, Demucs quality-flag detection off, the disk-space guard off (`DISK_MIN_FREE_MB=0`), and the mix cache, the trusted proxy hops and the login limits at their defaults (`MIX_CACHE_PER_SONG=6`, `FORWARDED_TRUSTED_HOPS=1`, `LOGIN_RATE_LIMIT_MAX_ATTEMPTS=5`, `LOGIN_RATE_LIMIT_WINDOW_SECONDS=60`), whatever a developer's `.env` says. Engines that need weights are exercised through fake worker processes and stand-in packages, so the suite runs offline. CPU-budget tests guard the DSP aligner's speed.
- **Frontend** (Vitest, jsdom). Contracts enforced by tests include unique accessible names in the studio at phone and desktop widths, 44 px touch targets, the dialog contract, a single never-remounting audio element, and design-token usage (no fixed palette colours in components).
- **Layout.** Each suite keeps one folder per feature: `backend/tests/` has `alignment`, `chords`, `lyrics`, `realignment`, `separation`, `media`, `subtitles`, `exports`, `render`, `projects`, `practice`, `vocal_range`, `server`, `workers`, `tools` and `e2e`; `frontend/src/tests/` has `accessibility`, `app`, `audio`, `chords`, `components`, `dialogs`, `export`, `intake`, `practice`, `pwa`, `shortcuts`, `stage`, `studio`, `theme`, `timeline`, `transport` and `ui`. Synthetic audio, media and fixtures shared between files live in each suite's `helpers/`. The `meta/` tests guard the layout: no test file at the top level, and on the backend unique basenames and no `__init__.py`, because pytest imports test files by basename.
- **Gates.**

  ```bash
  ruff check backend && ruff format --check backend && pytest
  cd frontend && npm run lint && npm run format:check && npx tsc -p . --noEmit && npm test && npm run build
  ```

- **Real-model checks** (on a machine that can download the weights): `backend/tools/fetch_models.py`, `benchmark_sync.py` (word error and confidence-vs-error against hand-timed words) and `benchmark_separation.py` (SI-SDR per preset against reference stems).
