# Karaoke Studio

Karaoke Studio turns a song from a link (YouTube, SoundCloud, Bandcamp, Vimeo, Internet Archive; Spotify, Apple Music, TIDAL and Deezer songs are matched to a YouTube upload) or an uploaded file into karaoke: it separates the vocals from the backing track, fetches lyrics and times them word by word, lets you fix the timing on a live timeline, lets you choose which vocal parts stay in the mix (backing vocals, one singer of a duet), and exports 1080p60 videos, `.lrc`/`.ass` subtitles and stems. A FastAPI backend drives FFmpeg, Demucs/RoFormer separation and an MMS/DSP lyric aligner; the React + TypeScript frontend is built to `frontend/dist` and served by the backend. Local-first, optionally behind a shared passphrase, AGPL-3.0.

Read next: `README.md` (features, every env var with its default) and `docs/ARCHITECTURE.md` (API table, persistence and concurrency rules, worker protocols, frontend hooks). Both are kept current with the code; `CHANGELOG.md` (written by release-please) lists every release.

## Commands

Run from the repo root: code imports `backend.*` and `pytest.ini` sets `pythonpath = .`.

```bash

INSTALL_ML_EXTRAS=1 ./run.sh    # also the RoFormer extras; TORCH_INDEX_URL picks another torch build (e.g. CUDA)

# Manual setup
python3 -m venv venv && source venv/bin/activate
pip install --extra-index-url https://download.pytorch.org/whl/cpu -r backend/requirements.txt     # includes pytest, ruff, modal
pip install --extra-index-url https://download.pytorch.org/whl/cpu -r backend/requirements-ml.txt  # optional: local Balanced/Best
cp .env.example .env

# Dev servers
uvicorn backend.main:app --host 0.0.0.0 --port 8000 --reload
cd frontend && npm run dev      # Vite on :5173, proxies /api and /static to :8000

# Gates, as .github/workflows/ci.yml runs them (Python 3.12, Node 20)
ruff check backend && ruff format --check backend && pytest
cd frontend && npm run lint && npm run format:check && npm test && npm run build   # build = tsc && vite build

```

## Architecture

- **No database.** Projects live in `projects.json` under `KARAOKE_DATA_DIR` (atomic writes, `.bak` recovery, `PROJECTS_LOCK`); media in `downloads/`, `stems/<track>/`, `output/`, `backgrounds/`, served at `/static/*`. The `projects` cache, job semaphores, cancel events (`active_cancellations`) and login rate limits are in memory, so run a single uvicorn process.
- **Server settings.** With `ADMIN_PASSWORD` set, the owner changes thirteen options from the studio's Server settings page (`components/admin/ServerSettingsDialog`, `GET`/`PUT /api/admin/settings`): song loops and their video models, the stem presets offered (`SEPARATION_PRESETS`) and their default, the cloud GPU, cloud rendering, both warm-ups, the longest song and album, the song search catalogs, the lyric timing engine. Saved values live in `<data dir>/settings.json` as the text their environment variable would hold and win over it (`backend/server_settings.py`); `services/admin_settings.py` lists, checks and saves them, and the list itself is `backend/assets/shared/server_settings.json`. See `docs/ARCHITECTURE.md` §2.1 (the owner) and §2.3.
- **Backend layout.** `backend/main.py` builds the app (auth and security-header middleware, static mounts, routers, service singletons). Routes are in `backend/routers/`, domain logic in `backend/services/`, RoFormer and MMS run as child processes from `backend/workers/`. Long jobs (`pipeline.py`, `render_worker.py`, `reseparation.py`, `realignment.py`, `vocal_split.py`) start as FastAPI `BackgroundTasks` and share `WORKER_SEMAPHORE` (`MAX_CONCURRENT_JOBS`); their status and progress live on the project, which the UI polls. `song_loop.py` starts the same way but only waits on the cloud, so it takes no slot (see 6c).
- **Song flow** (`pipeline.run_pipeline` for links, `run_local_pipeline` for uploads):
  1. Download with yt-dlp (`services/downloader.py`, retries several YouTube player clients; refuses live streams and recordings over `MAX_SONG_MINUTES` before downloading, and never reuses a WAV whose download did not finish). `services/media_links.py` turns a pasted link into its site and a file-safe track id (a YouTube video id, else `<site>-<id>`), which names the audio, the stems folder and the project, and refuses links that are not one song (profiles, albums, playlists; an Archive item of several recordings is refused after yt-dlp reads it). Sites and domains are in `backend/assets/shared/media_sites.json`. yt-dlp needs a Vimeo login for most videos, so those fail with a sign-in error. Spotify, Apple Music, TIDAL and Deezer are `lookup` sites: `services/song_lookup.py` reads the song's title, artist and length from the service's public page or API and picks a matching YouTube upload (same title, artist and length within 15 s, never another version), downloaded under the song's own track id; the song keeps the service's title and artist and records `song_match`. Those pages can change without notice; `song_lookup` is where to fix a service that stops answering. Typed words are searched instead (`services/song_search.py`, `POST /api/search/songs`): songs from Deezer's and the iTunes Store's public search APIs, respelled with YouTube's search suggestions or from the songs found, copies of one recording merged, and ranked here with a typo allowance (live takes, remixes and sound-alike acts below the song as released). A picked song starts as its Deezer or Apple Music link, so it takes the lookup path; with no catalog answering (or `SONG_SEARCH_SOURCES=none`) the studio lists YouTube uploads from `POST /api/search`.
  1b. Whole albums (`backend/album_pipeline.py`): a pasted link that is a whole album (`album_tracks.looks_like_album`: ten minutes or more, called an album or split into three song-length chapters) raises `downloader.AlbumDetected` from yt-dlp's `match_filter`, before anything downloads. The album is downloaded once, compressed (`download_album_audio`, `<track id>.album.<ext>`, up to `MAX_ALBUM_MINUTES`), its songs listed from its chapters, else the Deezer/iTunes album whose songs add up to its length, else its pauses (`services/album_tracks.py`), each cut moved to the quiet nearby (`services/album_audio.py`), and the project rests with status `album` and an `album` field. Uploads of ten minutes or more are checked the same way in `run_local_pipeline` (the file's own chapters, the catalog, or three songs told apart by pauses). `routers/albums.py` lists the songs (`GET …/album`), starts picked ones as projects `<album id>-tNN` with `album_track` (their pipeline calls `album_pipeline.song_audio`, which cuts the song out of the album instead of downloading), or makes the recording one song (`…/album/whole`, sets `album_whole`, which turns detection off for that project and its retries). The studio shows `album/AlbumTrackPicker`.
  2. Separate (`services/separator.py`) at the song's preset from `separation_presets.py`: fast = Demucs `htdemucs` (`python -m demucs`); balanced = Mel-Band RoFormer and best = Mel-Band + BS-RoFormer averaged, both through `workers/roformer_worker.py` locally or on Modal. Falls back best → balanced → fast; `process_watchdog.py` handles cancel, timeout and stall; provenance is stored as `project.separation`. Then vocal range (`vocal_analyzer.py`) and chords (`chord_detector.py`) start on threads of their own; the song goes `ready` without waiting for them, and the studio fetches whichever is missing (`GET …/chords`, `GET …/vocal-range`), which waits for the running analysis (`project_analysis._analysis_lock`).
  3. Lyrics (`services/lyrics.py`): LRCLIB, then `syncedlyrics`, or pasted text/LRC (kept on the song as `intake_lyrics` until it has its lines, so **Try again**, which sends `retry`, and an album made as one song use them again; `services/intake_lyrics.py`). A fan upload's "Artist - Song" title is split when the artist is only the channel (`downloader.track_artist`); candidates are scored by name, length and file quality (`lyric_quality`); when LRCLIB writes a repeated hook once (`writes_repeats_once`), NetEase's fuller version is taken if it passes `is_fuller_transcription`. Fetched lines go through `services/lyric_cleanup.clean_fetched_lines` (notes, "x2" markers, long lines, CJK romaji into `romaji`, all caps). The lookup starts on its own thread once title, artist and length are known and runs during separation (`pipeline.LyricsPrefetch`).
  4. Align (`services/lyric_sync.sync_lyrics`): DSP pass (`aligner.py`), then the neural MMS pass (`workers/ctc_align_worker.py`, one at a time via `ALIGN_SEMAPHORE`) when available; merged per line, scored by `sync_confidence.py`, summarized in `sync_report` (with `vocal_regions` and `uncovered_vocals`). A line with `romaji` is aligned on its romaji (`lyric_sync.romaji_onto_characters`). The model's emission for a stem is saved by vocals hash (`services/emission_cache.py`, `<data dir>/alignment_cache`), so later passes on the same vocals skip the model; with `SEPARATION_REMOTE=modal` the GPU computes it right after separation.
  5. In `pipeline.sync_project_lyrics`, right after alignment: `services/repeat_fill.fill_repeats` adds the hook repeats the lyrics left out (neural engine only, lines marked `added: "repeat"`), then `services/voice_parts.assign_voice_parts` sets Singer 1 / Singer 2 by voice while every line is still Singer 1 (`project.voice_parts`). Then the first master mix (`audio_mixer.mix_and_shift`) and status `ready`.
  6. Editing: the studio saves lines (`POST /api/project/{id}/lyrics`), remixes key and guide vocal (`/mix`, cached), re-times one line (`realign-line`, saves nothing), splits and merges lines (`utils/lineSplitMerge.ts`), assigns parts by voice (`GET …/voice-parts`, applied as an edit) and names them (`part_names` via `PATCH /api/project/{id}`), and starts background jobs on finished songs: `sync_job` (`realign-lyrics` with `background: true`), `separation_job` (`reseparate`) and `vocal_split_job` (`vocal-split`). `background_jobs.conflict_reason` blocks overlaps with 409.
  6b. Vocal parts: `POST …/vocal-split` (`backend/vocal_split.py`) runs one more RoFormer model over a vocal stem (`separator.split_vocals`, no fallback engine) and keeps its two outputs beside the stems (`services/vocal_parts.py`): `lead_backing` gives `vocals_lead.wav` + `vocals_backing.wav`, `male_female` splits the lead (else the whole vocals) into `vocals_male.wav` + `vocals_female.wav`. Which parts exist is read from the files (`vocal_parts.current_parts`: both present and no older than their source), never from the project; `vocal_splits` on the project is a copy for the studio. Replacing `vocals.wav` deletes the parts. The song's `vocal_levels` (sent with `/mix` and `/render`) say which vocals a mix keeps: `backing`, and the lead `by: "lines"` (`singer1`/`singer2`/`both`, applied during those singers' lyric lines) or `by: "voices"` (`male`/`female`). `services/vocal_mix.plan_mix` decides; `master_audio.make_master_mix` is the one way to make a mix after the intake's first (it calls `audio_mixer.mix_and_shift` unchanged, with a temporary "kept vocals" file as the vocal input when the levels need one, and names that mix `…_<8 hex>.wav`). Lines saved or re-timed under a mix that follows them set `master_stale`, which the studio answers with a new `/mix`.
  6c. Song loop (only with `SONG_LOOP_REMOTE=modal`): `POST …/song-loop` (`backend/song_loop.py`, `song_loop_job`) sends the lyric lines, or a typed scene (`prompt`), to the Modal function `song_loop`, which runs `workers/song_loop_worker.py`: a language model writes one scene from the lyrics, a video model (the request's `model`, else `SONG_LOOP_MODEL`: `wan22`, shown as Best, or `ltx`, Fast; `SONG_LOOP_MODELS` limits which the studio offers, and their names, minutes and notes are data in the worker's `MODELS`) draws a few seconds of it, and FFmpeg crossfades the clip into its own start (`loop_filter`). The job checks the result with ffprobe and keeps it as `output/<id>_loop.mp4`, recorded as `song_loop` on the project (`services/song_loops.py`); a failed run keeps the old loop. It reads nothing the other jobs change, so `background_jobs.conflict_reason` does not know it: it runs beside them, one loop at a time across the server (`SONG_LOOP_SEMAPHORE`). The stage background style `loop` shows it (`StudioWorkspace` passes it to the stage as an uploaded video; a song without one shows cover art), and a render with `background_style: "loop"` gets the file as its custom background in `render_worker`. The control is `components/look/SongLoopControl`, hidden where the server has no `SONG_LOOP_REMOTE` and the song has no loop (`utils/songLoop.showsSongLoop`).
  7. Export: `/render` → `render_worker` mixes at final quality (Rubber Band), writes the `.ass` file in the song's look (`ass_generator.py` → `ass_style.resolve_look_style` → `ass_look.generate_look_ass`) and renders with FFmpeg + libass (`video_renderer.py`, bundled stage fonts in `backend/assets/fonts`), locally or on Modal. LRC, ASS, chord sheet, stems and the YouTube kit are plain GET routes.
- **Frontend** (`frontend/src`): React 18, strict TypeScript, Vite, Tailwind; no router or state library. `App.tsx` switches between the library (`TrackSearch`), `ProcessingView` and `studio/StudioWorkspace` (stage, timeline, inspector); the intake box searches typed words as the typing pauses (`hooks/useSongSearch`) and lists the songs under it with a preview of each (`track-search/SongSearchResults`, `hooks/useSongPreview`), with YouTube uploads on request; `transport/TransportDock` owns the only `<audio>` element. Practice (`hooks/usePractice`, `components/practice/PracticePanel`; the song header's button, P, or `?practice=1`) puts a panel in the timeline's place for rehearsing the song: a part of it repeats (`hooks/usePracticeLoop`, parts from `utils/practiceSections`, the rule in `utils/practiceLoop`); see `docs/ARCHITECTURE.md` §3.2. `/?stage=1` is a stage window, the stage alone for a second screen: `main.tsx` mounts `stage-window/StageWindow` there in place of `App`, and the studio's stage keeps it in step over a `BroadcastChannel` (`utils/stageLink`, `hooks/useStageLeader`; see `docs/ARCHITECTURE.md` §3.5). `/?show=1` is a show, the host screen of a karaoke night (`show/ShowApp`, also mounted by `main.tsx`): a queue of singers kept in the browser (`utils/showQueue`), each with a library song or a YouTube karaoke video; `hooks/useShowPlayer` plays a library song in the host's window and a video in the stage window (`stage-window/StageVideo`, YouTube's IFrame Player API), the host screen shows that video once more without sound (`show/ShowStageMonitor`, kept in step by `utils/stageMonitor`), and the backend's `services/show_videos.py` (`/api/show/videos/*`) says whether YouTube will embed a video and keeps a copy of one it will not. Behaviour lives in `hooks/` (polling, audio, mix, editor history, quality jobs, command palette), pure helpers in `utils/`, design-system primitives in `components/ui/`, the stage looks in `theme/`, and the app's one look as CSS variables in `index.css` (see **The look** under Conventions). The Audio mix panel (`components/AudioControls`) holds the key, the guide vocal, the vocal parts (`audio/VocalPartsControl` with `audio/VocalSplitControl`; levels in `useMixController`, helpers in `utils/vocalLevels`) and the stems' quality. `api.ts` (`apiFetch`) adds the auth headers. `types.ts` mirrors `backend/schemas.py` by hand. `useProjectHistory` keeps `?project=` in the address bar and gives each opened song a history entry, so Back returns to the library. Guidance for new users: the first-song card (`studio/FirstSongCard`, `useFirstSongGuide`), the song check-up (`utils/songCheckup`, `studio/SongCheckupDialog`, opened from the song header) and Help's "Fix a problem" tab (`utils/troubleshooting`); their buttons are `GuideAction`s (`utils/guideActions`) that `useGuideActions` carries out, opening the timeline's tools through the palette's `runCommand(id)`; the failed screen's plain-language reasons are in `utils/processingErrors`; the guide (`components/guide`, a deferred chunk) points at the screen itself: a tour of the studio or the home screen (`utils/guideStops`) and "Show me" for each feature of Help's "What you can do" tab (`utils/features`, `help/HelpFeatures`), finding controls by their `data-guide` attribute (`utils/guideAnchors`) and offered from the first-song card, "How it works", Help and the palette (`useGuideCommands`); see `docs/ARCHITECTURE.md` §3.6. First load: `index.html` paints a boot shell, fonts are self-hosted (`src/fonts.css`), and the studio, export/help dialogs and command palette are deferred chunks (`deferredScreens.ts`) that `main.tsx` preloads when idle; the home screen opens on a headline that is sung once (`track-search/SungHeadline`) and the setlist loads card-sized entries (`GET /api/projects?summary=1`), fetching a song in full when it is opened; see `docs/ARCHITECTURE.md` §3.6. Installable-app pieces: `public/` (`manifest.json` with a share target and app shortcuts, `sw.js`, `offline.html`, icons, screenshots), `utils/installPrompt` + `useInstallPrompt` + `InstallAppDialog`, `utils/sharedLink`, `utils/appShortcut` (`/?shortcut=new|upload|resume`), `useScreenWakeLock` (screen stays on while playing), and `utils/serviceWorker`. Android paints the bar under the gesture pill from the manifest's `theme_color`, not the page, so the manifest, `index.html` and the `:root` tokens carry the same black (`tokenParity.test.ts`); see `docs/ARCHITECTURE.md` §3.7.

## Cloud offload (Modal)

- `gpu/modal_app.py` defines the Modal app (default name `karaoke-studio-gpu`): `separate` runs `roformer_worker` unchanged on the first free GPU (`A10G,L40S,L4,T4`), then `ctc_align_worker --emission` on the new vocals (best effort; the emission comes back with the stems), with weights in the Modal volume `karaoke-models` (unrelated to the Docker volume of the same name); `render` runs FFmpeg on 16 CPUs with `backend/assets/fonts` mounted at `/fonts`; `song_loop` runs `song_loop_worker` on a 48 GB class GPU (`SONG_LOOP_REMOTE_GPUS`, default `L40S,A100-80GB`: LTX-Video keeps every part on the GPU and ran out of memory on a 40 GB A100, where Wan 2.2, whose parts take turns, still ran) in its own image (`loop_image`: diffusers and transformers, which the server never installs), with its weights (tens of GB, downloaded on the first loop) under `/models/loops` in the same volume. `modal run gpu/modal_app.py::song_loop_trial --lyrics a.txt,b.txt --out DIR` makes loops with each video model in an ephemeral app, to compare them.
- Deploy with `modal deploy gpu/modal_app.py` after `modal setup`. Deploy-time env: `SEPARATION_REMOTE_APP`, `SEPARATION_REMOTE_GPUS`, `SEPARATION_REMOTE_SCALEDOWN_SEC` (30), `SEPARATION_REMOTE_TIMEOUT_SEC` (1800, the `separate` function's own limit; the server's `SEPARATION_TIMEOUT_SEC` can only stop a job sooner), `RENDER_REMOTE_CPUS` (16), `SONG_LOOP_REMOTE_GPUS`, `SONG_LOOP_REMOTE_TIMEOUT_SEC` (2400), `SONG_LOOP_REMOTE_SCALEDOWN_SEC` (30). Redeploy by hand after changing the RoFormer, CTC or song loop worker, `backend/requirements-ml.txt` (installed with `audio-separator[gpu]`), the fonts or the render image's system packages (`render_image`, which installs the app image's font packages, Noto CJK included; `test_render_image_fonts.py` keeps the two lists in step); nothing redeploys it automatically.
- Server toggles: `SEPARATION_REMOTE=modal` (Balanced, Best and the vocal splits; Fast always runs locally), `RENDER_REMOTE=modal` and `SONG_LOOP_REMOTE=modal` (song loops, which have no local path; limits `SONG_LOOP_REMOTE_QUEUE_SEC` 300, `SONG_LOOP_TIMEOUT_SEC` 2400, `SONG_LOOP_STALL_SEC` 300). Credentials: `MODAL_TOKEN_ID` + `MODAL_TOKEN_SECRET` in `.env` (a `~/.modal.toml` also counts). `SEPARATION_REMOTE_APP` must match the deployed name. Limits: `SEPARATION_REMOTE_QUEUE_SEC` (300), `RENDER_REMOTE_QUEUE_SEC` (120), `RENDER_REMOTE_TIMEOUT_SEC` (3600); remote separation also obeys `SEPARATION_TIMEOUT_SEC` and `SEPARATION_STALL_SEC`. Opening the Export dialog sends a beacon to `POST /api/render/warmup`, which starts a cloud CPU at most once a minute (`RENDER_REMOTE_PREWARM`, on by default) so the render doesn't wait for one. Likewise a Balanced or Best intake starts a GPU while its audio downloads (`remote_separation.warm_up`, `separate(warmup=True)`, at most every 20 s; `SEPARATION_REMOTE_PREWARM`, on by default).
- Readiness is checked offline (package and credentials present). Deploy or capacity problems surface at job time as `RemoteUnavailable`: separation skips the other cloud presets and runs Fast locally; a failed or unavailable cloud render renders locally.
- Server side: `services/modal_jobs.py` (spawn, follow an ephemeral queue, cancel), `remote_separation.py`, `remote_render.py`, `remote_song_loop.py`. Kept in sync by hand with `gpu/modal_app.py`: the `STARTED` marker, `FONTS_DIR`, function names and kwargs (every `separate` kwarg has a default, and the server sends `first_tags`/`second_tags` only for a plan that has them, so an older deployment keeps working for everything else), and the result keys (`vocals`, `no_vocals`, `emission`, `video`; for `song_loop` also `remote_song_loop.RESULT_KEYS`, which the worker writes to `result.json`). Every `song_loop` kwarg has a default too, and the server leaves out empty ones. `render` takes the font files the subtitles need (`fonts`, sent only when a render names some) and refuses the render when its `/fonts` lacks one, so the server renders locally instead of getting a video in a fallback font. Tests fake the `modal` module, and `backend/tests/conftest.py` unsets every remote/Modal variable.

## Deployment

- Production runs in a Proxmox LXC (CT 112) on the owner's homelab: Docker-in-LXC, using this repo's `Dockerfile` and `docker-compose.yml` from a clone at `/opt/karaoke-studio`, behind Nginx Proxy Manager. The provisioning script (`scripts/deploy_karaoke_lxc.sh`), a reference compose copy (`docker/karaoke-studio/`) and the ops doc (`docs/homelab/services/karaoke.md`) live in the homelab repo (kepler).
- **Pushing to `main` deploys.** A systemd timer runs `update.sh` every 30 minutes. It should call this repo's `scripts/update_when_idle.sh`, which runs `git fetch`, moves to the new commit only once its CI run on GitHub has passed (see below), builds the image while the old container keeps serving, then drains: it writes `<data dir>/.update_draining`, and the server answers 503 to new jobs (`backend/update_drain.py`). It waits until `<data dir>/.jobs_active` reports 0 jobs (or goes stale, or `UPDATE_DRAIN_MAX_SEC`, 45 minutes by default, passes), then runs `docker compose up -d`. Before that script existed, `update.sh` ran `docker compose up -d --build` directly and cut running jobs off, without waiting for CI. After the restart it writes the commit to `<data dir>/.update_deployed`, and "nothing to update" is decided from that file, not from the checkout's HEAD (which stands in only until the file exists). If the build fails, the old container keeps running, nothing is paused, and every later run builds again until one succeeds, so a build that keeps failing needs a fix pushed.
- **The updater's CI check.** `update_when_idle.sh` asks GitHub for the newest run of the `ci.yml` workflow on the commit it is about to move to. Passed: it updates. Failed (anything but `success`): it stays on the running commit and tries again on every later call, so a fix pushed to `main` goes out by itself. Still running: it waits up to `UPDATE_CI_WAIT_SEC` (900), then leaves it for the next call. No result to read (the API cannot be reached, the origin is not on GitHub, the commit has no CI run after two minutes): it updates and logs why, as it did before the check existed, but only for a commit it has never seen failed or running. The commit last seen failed or still running is kept in `<data dir>/.update_ci_hold`; for that commit "no result" means stay, until a run passes or a newer commit arrives. `--force` does not skip the check when there is a new commit; `UPDATE_REQUIRE_CI=0` does. It resets to the commit it checked, not to wherever the branch is by then. A private repository needs `UPDATE_CI_TOKEN`. Renaming the CI workflow file means setting `UPDATE_CI_WORKFLOW` on the server, or the check finds no run. The **Update now** toast does not know about CI: with a red `main` it still offers an update that the updater then declines.
- Forced update: `POST /api/system/update` (or `POST /api/health`) with `{"action": "update"}` writes `<data dir>/.update_requested`, which a systemd path unit turns into an immediate update. Both routes need a session when `APP_PASSWORD` is set, so scripts send `X-App-Password`. With `SELF_UPDATE=1` (prod `.env`) the studio itself offers an "Update now" toast when GitHub's `main` is ahead (`hooks/useServerUpdatePrompt.ts`); it stays off elsewhere, where nothing applies the request.
- Prod config exists only in CT 112's `.env`, which updates leave alone: `SEPARATION_REMOTE=modal`, `SEPARATION_QUALITY=best`, `RENDER_REMOTE=modal` and a dedicated Modal token. New env vars need safe defaults. An untracked `docker-compose.override.yml` there sets `ulimits: core: 0`.
- The prod CPU has AVX but no AVX2/AVX-512: local RoFormer is very slow there and PyTorch can die with SIGILL, so Balanced and Best depend on Modal and Fast is the local fallback. 4 vCPUs, 6 GB RAM, a 40 GB disk shared with Docker's build cache.

## Conventions

- Python: ruff for lint and format (target py312, line length 100, double quotes; rules in `pyproject.toml`). Modules open with a docstring. Reach shared singletons (`separator`, `audio_mixer`, `lyrics_service`, `WORKER_SEMAPHORE`, `projects`, ...) through `import backend.main as main_mod` at call time; tests monkeypatch them there. Background jobs look the project up again before every write and save under `PROJECTS_LOCK`. Request handlers that report an edit as saved call `save_projects(strict=True)` inside `restore_on_failed_save(proj, keys)`, so a full disk answers 507 and rolls the edit back; background and progress saves stay soft. Routes that start new work (`/process`, uploads, `/render`, `/reseparate`) call `ensure_free_space()` after their 404, 409 and request checks (an upload's file-content check comes after).
- Frontend: Prettier (single quotes, semicolons, width 100), ESLint with `--max-warnings 0` (warnings fail CI), strict TS. Colour only through theme tokens (`bg-theme-*`, `text-theme-*`): `designTokenGuard.test.ts` fails on Tailwind palette classes like `bg-slate-800` in `components/` or `App.tsx`. Modals use `components/ui/Dialog`; tests enforce 44 px touch targets and unique accessible names at phone and desktop widths.
- The look ("Marquee", `docs/ARCHITECTURE.md` §3.1): black, off-white and one yellow, with no themes. Yellow means lit: what is playing or on, and the one action that moves a song forward on a screen; never decoration. Only exceptions get colour or a label. A 2 px rule divides regions and a hairline divides rows; only controls have an outline, never nested, so new UI is rows and sections, not cards. Names and actions are condensed capitals (`ks-display` with a `text-[20px]` or larger size class); everything else is sentence-case text. Capitals come from CSS: write sentence case in the DOM (a `<button>` inside a `ks-display` heading needs its own `uppercase`, since Tailwind resets it). No radius, shadow, gradient, blur, glow or tinted fill outside the stage files, and no sparkle icons (`flatLookGuard.test.ts`). Wording is plain: no "AI", "Smart" or status chatter (`plainWordsGuard.test.ts`). Monospace is for keycaps, pasted lyrics and raw error text; numbers use `tabular-nums`.
- Tests: one folder per feature, `backend/tests/<feature>/test_*.py` (alignment, chords, subtitles, render, projects, server, ... and `e2e/`) and `frontend/src/tests/<feature>/*.test.ts(x)` (stage, timeline, transport, theme, accessibility, pwa, ...; Vitest, jsdom, Testing Library). `backend/tests/conftest.py` and `frontend/src/tests/setup.ts` stay at the top and cover every folder. Shared generators and fixtures go in each suite's `helpers/`, never in another test file. pytest imports test files by basename (there is no `__init__.py`), so a new file's name must be unique across folders; the `meta/` layout tests check that and that no test file sits at the top level. File names say what the file tests (`test_chords_api_backfill.py`, `transportDockScrubbing.test.tsx`); 2.0-era files also use sentence-style test names, while older files' docstrings and test names still carry labels from earlier agent runs (`Challenger`, `Milestone`, `iter2`). ML engines run as fake worker processes and stub packages, so neither suite needs model weights or network; tests that reach the NetEase step stub `syncedlyrics.search`. `conftest.py` makes `song_search._get_json` raise, so a test that searches songs replaces it with `helpers/song_catalogs.FakeCatalogs`, which replays what Deezer, iTunes and the suggestions really answered for misspelled searches (`helpers/song_catalog_listings.json`). Real lyric listings of two songs (LRCLIB and NetEase) are in `backend/tests/helpers/lrclib_listings.py`, synthetic one- and two-voice stems in `helpers/voices.py`.
- Commits: Conventional Commits, `type(scope): summary`, the summary in plain lowercase English describing the effect (`fix(stems): keep lyric edits saved while a re-separation re-times words`). Types: feat, fix, docs, test, style, chore. Bodies are wrapped prose on what was wrong and what changed.
- Releases are cut by release-please (`.github/workflows/release-please.yml`, `release-please-config.json`, `.release-please-manifest.json`). It keeps a release PR (`chore(main): release X.Y.Z`) open on `main` that collects the commits since the last release, bumps `DEFAULT_APP_VERSION` in `backend/config.py` (the line marked `x-release-please-version`), `version` in `frontend/package.json` and its lock, and writes `CHANGELOG.md`. Merging that PR tags the commit `vX.Y.Z` and publishes a GitHub Release. Do not bump those versions, edit `CHANGELOG.md` or tag by hand. The version comes from the commit subjects on `main` (the PR title, with squash merges): `fix` is a patch, `feat` a minor, `feat!`/`fix!` or a `BREAKING CHANGE:` footer a major; `docs`, `test`, `style` and `chore` alone release nothing and stay out of the changelog. To force a version, put `Release-As: X.Y.Z` in a commit body. The running version is `APP_VERSION`, else `git describe --tags --always` (compose mounts `.git` read-only; asked once per server process, like the commit `GET /api/health` reports), else that default. The README's "What's new" sections are hand-written highlights and optional.

## Gotchas

- `backend/config.py` reads the repo-root `.env` at import (real env vars win) and creates the `KARAOKE_DATA_DIR` folders (default `./workspace_data`) on import. It also reads `ALLOWED_ORIGINS` (comma-separated CORS list) and `APP_VERSION`, which `.env.example` does not list.
- Auth: an empty `APP_PASSWORD` means open access. When set, `/api/*` (except `GET /api/health` and `/api/auth/*`) and `/static/*` need a session token or the raw passphrase (`X-App-Password`, `Authorization: Bearer`, or a cookie); without one, `GET /api/health` ignores `check_remote`. Wrong passphrases at login and in headers or cookies on any route share one rate limit (each distinct value once per window; expired tokens signed with the passphrase don't count), and a limited IP gets 429 even with valid credentials. It keys on the `X-Forwarded-For` entry `FORWARDED_TRUSTED_HOPS` places from the end (default 1, the nearest proxy's; cloudflared in front of Nginx Proxy Manager needs 2), so port 8000 must only be reachable through the proxy. Tokens are HMAC-signed with a key derived from the passphrase and the server secret (`SESSION_SECRET`, else `<data dir>/.session_secret`, created on first use) and last 7 days, so changing either signs everyone out; tests that hand-sign a token use `auth.session_signing_key`. `conftest.py` sets a test passphrase when none is set: use the `client` fixture, or `unauth_client` for 401 cases.
- The show-only sign-in (`SHOW_PASSWORD`, `backend/show_auth.py`): a show token opens only the requests listed in `show_auth.ALLOWED` (method and whole path) and gets 403, never 401, for the rest, so a route the host screen starts calling must be added there or a venue's show breaks while the owner's keeps working. Add only reads and the show's own routes: the list is what keeps a venue from changing the library (`tests/show/test_show_sign_in.py` pins both sides). The frontend sends the token in `X-Show-Token` only (`api.ts`); in the studio's headers it would count as a wrong studio passphrase. `conftest.py` empties `config.SHOW_PASSWORD`.
- Models download on first use into `TORCH_HOME`, `AUDIO_SEPARATOR_MODEL_DIR` and `ALIGNMENT_MODEL_DIR` (Docker: the `karaoke-models` volume at `/models`): Demucs about 80 MB, each RoFormer 0.6–0.9 GB, MMS about 1.2 GB. The MMS aligner is CC-BY-NC 4.0 (non-commercial); `ALIGNMENT_ENGINE=dsp` never uses it. The `librosa<1.0` pin in `requirements-ml.txt` is deliberate (audio-separator 0.47 needs audioread).
- Never commit `.env`, `client_secret.json`, `token.json`, `workspace_data/` or `frontend/dist/`. `.gitignore` also ignores every `*.png`, `*.jpg`, `*.webp`, `*.wav`, `*.mp4` and `*.ass` outside `docs/` and `frontend/public/`; tests generate their media at run time.
- Shared with the frontend: `backend/assets/shared/*.json` (the stage looks, their font metrics and the stage's case files, singer labels, song-link sites and their host cases, upload limits, the longest title, artist, singer's name and lyrics (`text_limits.json`, read by the request models and by every field that takes one), confidence thresholds, background motion, tokenizer cases, word-spread cases, ad-lib cases, uncovered-vocals thresholds), read by `backend/shared_assets.py` and imported by the frontend as `@shared/<name>.json`; the Docker frontend stage copies that folder. Still hand-synced: the app's colours across `index.css` (`:root`), `tailwind.config.js`, the boot shell in `index.html`, `public/manifest.json` and `public/offline.html` (the first four compared by `tokenParity.test.ts`); the lyric tokenizer in `backend/services/lyric_tokenize.py` and `frontend/src/utils/lyrics.ts`, with how tokens are written back out (`space_after`/`join_lyric_tokens` and `spaceAfterTokens`/`joinLyricTokens`: the source text's spacing, never spaces around CJK characters) (both suites run `backend/assets/shared/tokenize_cases.json`, whose `written` and `joined` fields pin the spacing); the ad-lib rule, words inside parentheses (`adlib_flags` in `lyric_tokenize.py`, `adlibFlags` in `utils/lyrics.ts`; both run `adlib_cases.json`); the vocals-without-lyrics rule (`sync_confidence.uncovered_vocals`, `utils/uncoveredVocals.ts`; thresholds in `uncovered_vocals.json`); the editor's even word spread in `backend/services/lyric_sync.py` (`words_spread_evenly` and its helpers `_spread_weight`, `_SPREAD_PUNCTUATION` and `SPREAD_TOLERANCE`), mirrored by `frontend/src/utils/lyrics.ts` (`wordSpreadWeight`) and `utils/manualEdits.ts` (`wordsSpreadEvenly`, `SPREAD_TOLERANCE`) (both suites run `backend/assets/shared/word_spread_cases.json`).
- Server settings: an option the Server settings page can change must be read through `server_settings.env("NAME")` (or one of its three `config` functions), never `os.getenv`, or a saved value is ignored. Adding one means an entry in `backend/assets/shared/server_settings.json`, a reader in `admin_settings.READERS` (`test_admin_settings_api.py` fails when the two disagree) and an entry in the frontend test fixture `tests/helpers/serverSettingsFixtures.ts`. `backend/server_settings.py` must import nothing from the app at import time (the RoFormer worker imports it through `separation_presets` on the cloud GPU; `test_server_settings_store.py` checks). The admin routes answer 403, never 401: `apiFetch` signs the studio out on any 401. `conftest.py` sets `config.ADMIN_PASSWORD` to empty and forgets saved settings between tests.
- Stage looks (**one frame for the stage and the video**): the five looks are data in `backend/assets/shared/stage_looks.json` (layout, colours, faces, where everything sits, in u = 1% of the frame's short side; em sizes and baselines). Four rules exist once in Python and once in TypeScript and must give the same answers: when things show (`stage_timing.plan_timeline` / `utils/stageTimeline.ts`), line fitting (`text_fit.py` / `utils/stageFit.ts`), placement (`stage_layout.py` / `utils/stageLayout.ts`) and what is drawn at a moment (`ass_layout_*.py` + `ass_frame.py` / `utils/stageScene.ts`). After changing any of them or the spec, run `python -m backend.tools.stage_cases` and read the diff: both suites run the four `stage_*_cases.json` files and `looks/test_stage_cases_current.py` fails when one is stale. Neither side measures or wraps text itself (widths come from `stage_font_metrics.json`; `WrapStyle: 2`); rounding is half up on both sides (Python's `round` is not). Inside the stage frame use only what libass can draw (flat fills, an outline, one soft shadow, opacity, straight moves that are functions of the song time, never CSS transitions). libass takes a font's cell height as its size and finds a static cut by its legacy family name: `test_libass_assumptions.py` pins the facts the looks rest on. The nine old preset ids (`afterglow`, `modern_gold`, ...) still resolve through `legacy_ids`; a tab from before the looks sends its preset's own colours, which `resolve_look_style` does not take for a choice.
- Uploaded stage backgrounds: an upload's id lives only in the stage settings of the browser that sent it (one upload per browser, shown behind every song), so the server cannot tell which files are in use. The studio asks for the old file to be deleted when it replaces or removes its upload (`useVisualTheme.setCustomBgId`, `DELETE /api/background/{id}`), and `POST …/render` holds the request's upload until the render ends (`services/uploaded_backgrounds.py`), so never delete from `backgrounds/` anywhere else.
- Service worker (`frontend/public/sw.js`): it must never handle `/api` or `/static` or serve the page from cache, or audio, projects and the reload prompt (`useUpdatePrompt`) go stale. Bump its cache names when changing what it precaches. `sw.js`, `offline.html` and `manifest.json` are served `no-cache` (`backend/http_delivery.py`). It only registers in production builds.
- Never put `overscroll-behavior: none` or `contain` on `body`: `html` and `body` both set `overflow-x: hidden`, so `body` is a scroll container that never scrolls, and blocking its overscroll kills touch scrolling on phones. Put it on `html` (`standaloneScrollGuard.test.ts` checks).
- Fonts: the page loads nothing from other sites. An interface font needs its `@fontsource` package, an entry in `frontend/scripts/generate-fonts-css.mjs` and `npm run fonts` (`src/fonts.css`). A stage look's font needs that (in `src/stageFonts.css`) and the same cut as a static TTF with its OFL text in `backend/assets/fonts` and `backend/assets/licenses`, an entry in `backend/tools/font_metrics.py`, `python -m backend.tools.font_metrics`, then `python -m backend.tools.stage_cases`, and a redeploy of the Modal app (until then cloud renders are refused and run locally). `selfHostedFonts.test.ts` and `looks/test_font_metrics.py` fail when the sheets, the table and the files disagree. Never import a `@fontsource-variable` package's CSS directly: it names the family "Sofia Sans Variable", which no stack uses.
- First-run UI (the first-song card) renders in every App-level test, because `tests/setup.ts` clears storage after each test: give its controls names no other studio control has (`studioAccessibleNameUniqueness.test.tsx`), keep it out of non-wrapping flex rows (the overflow checks estimate a button's width from all its text, `sr-only` included), and never give in-page guidance `role="dialog"`, which turns the keyboard shortcuts off (`isModalActive`). `LyricTimelineEditor.tsx` has a 430-line limit enforced by tests: new timeline UI goes in a child component.
- Practice never remounts the studio: `usePractice` is called by `App` whether practice is on or not, and its panel reaches the editor as a node (`practicePanel`), so unsaved lyric edits stay in the timeline behind it. The hidden timeline panel carries both the `hidden` attribute (which takes it out of the accessibility tree and Testing Library's) and the `hidden` class (Tailwind's `block` would otherwise win over the attribute). New practice UI goes in `components/practice`, never in the editor, and its control names must be unique across the whole studio with practice on (`studioAccessibleNameUniqueness.test.tsx` runs both): the two line lists name the same lines, so the second list's options carry an `aria-label`.
- The guide (`components/guide`): a tour may be a dialog because it only ever opens when asked for; anything shown unasked, and the note that points at one control ("Show me"), may not. A stop finds its control by a `data-guide` name, so renaming or removing a control that has one means changing `utils/guideStops.ts` or `utils/features.ts` too (`tests/guide/guideAnchorsInApp.test.tsx` fails otherwise), and a control that is not on every server or song is marked `optional` with a `missing` sentence. jsdom lays nothing out, so placement is tested as sums (`utils/guidePlacement`) and anything about where the ring lands needs a real browser. `GuideTour`'s effects press buttons and pause the song: keep each safe to run twice (React's strict mode does, in development).
- Guidance copy is in two places kept in step by hand: `frontend/src/utils/troubleshooting.ts` (Help's "Fix a problem") and the README's "When results are off" table. The tour's stops and the features of "What you can do" (`utils/guideStops.ts`, `utils/features.ts`) are written once, but they describe controls in words: change them when a control's name or what it does changes.
- The stage window (`/?stage=1`) has no player, no sign-in and no saved settings: everything it shows is sent by the studio's stage, so a new stage input (a prop of `LyricDisplay` that changes what is drawn) must be added to `StageState` in `utils/stageLink.ts`, to the `stageState` memo in `LyricDisplay` and to `StageWindow`, or the TV shows something else than the studio. The messages are copied between windows, so they hold plain data only. Tests get an in-memory `BroadcastChannel` from `tests/setup.ts`; two windows in one test render into two containers (`tests/stage-window/stageWindowFollowsStudio.test.tsx`).
- Show videos: YouTube refuses music in its embedded player on a page served from `localhost` or an IP address (error 150 for every karaoke video, while other videos play), so in development every karaoke video takes the copy path and embedding can only be tried on a real domain. The copy is asked for with yt-dlp's own choice of YouTube clients first (`show_videos.CLIENT_PROFILES`): the clients the song downloader names are offered only a 360p file. `conftest.py` makes `show_videos._oembed` answer nothing, so a test that needs YouTube's answer replaces it; frontend tests put `tests/helpers/fakeYouTube.ts` on the page in place of the IFrame API, which the app otherwise loads from youtube.com (the one script it takes from another site, and only where a video is about to play: a stage window, and the host screen's silent monitor of it). The fake tells the two players apart as YouTube does, by the `mute` player variable: `FakeYouTubePlayer.current` is the stage window's, `.monitor` the host screen's. The monitor must stay silent and must never be sent the host's volume: the room's sound is the stage window's alone. `/api/show/videos/{id}` takes the id alone: it names a file in the data folder.
- Song requests (`services/show_requests.py`, `<data dir>/show_requests.json`): the songs a show's host could not find, filed from Add a singer (`POST /api/show/requests`) and listed on the host screen and on the studio's home screen (`hooks/useSongRequests`). A show sign-in reads the list and adds to it; only the studio removes (`DELETE`, deliberately not in `show_auth.ALLOWED`). The home screen asks for the list on every load, so a test that counts or routes requests there sees `GET /api/show/requests`; an answer that is not a request list shows nothing.
- Deferred screens: components imported through `deferredScreens.ts` render asynchronously the first time in a test. A test that opens the studio, a dialog or the palette and asserts synchronously needs `beforeAll(() => loadDeferredScreens())`. Do not import them in `tests/setup.ts` (modules loaded there escape `vi.mock`).
- The manifest's icons and screenshots are committed PNGs in `frontend/public`, as is `og-image.png` (the link preview, a 1200×630 capture of the first-visit home screen). Regenerate them (from `icon.svg` / `icon-maskable.svg`, and a `seed_demo` library for screenshots) when the icon or the look changes; `tests/pwa/pwaManifestInstall.test.ts` checks their sizes against the manifest. The app shortcuts' icons (`frontend/public/shortcuts/*.png`) are rendered from the SVGs beside them at 96 and 192 px; `tests/pwa/appShortcuts.test.tsx` checks them.
- Changing what the mixer produces: bump `MIX_CACHE_VERSION` in `backend/master_audio.py` so cached mixes and older renders are rebuilt. Changing what the kept vocals of the same levels and lines sound like (the line gate's margins or fades, how parts are summed): bump `VOCAL_MIX_VERSION` in `services/vocal_mix.py`, which renames those mixes.
- Practice vocals (`master_audio.make_practice_vocal`, `POST …/practice-vocal`): the vocal stem alone at a key, which practice plays beside the master. The file's name must stay a mix name (`practice_vocal_filename`, matched by the pattern in `prune_mix_cache`): that is what prunes it, dates it against the stems and deletes it with the song, and a name outside the pattern is never cleaned up. The mixer must keep giving a lone input the chain it gives the backing of a master at that key, or the vocal drifts from the master (`test_practice_vocal_in_step_with_master.py`). The route is not in `show_auth.ALLOWED`: practice is the studio's.
- Two modules with near-identical names: `services/voice_parts.py` labels lyric lines Singer 1 / Singer 2 by voice (no audio is split); `services/vocal_parts.py` is the part stems a vocal split leaves on disk. A vocal split has no cheaper engine to fall back to, and the male/female one needs a Modal app deployed since the worker gained `--first-tags`; its model's output tags (`male`, `female`) are data in `vocal_parts.SPLITS`, and a wrong tag fails the job with the tags it asked for and the files it got.
- `pytest.ini` always adds `--cov=backend` and `pyproject.toml` sets `fail_under = 50`, so running a subset can fail on coverage alone (pytest-cov's `--no-cov` turns it off). A few tests assert wall-clock budgets and can flake on slow CPUs. CI installs FFmpeg with libass (`ffmpeg libass-dev`) for the backend suite; a couple of tests skip without FFmpeg or its rubberband filter.
- `run.sh` rebuilds `frontend/dist` only when it is missing or the `frontend/src` directory itself is newer, so edits to existing files can leave a stale build. The backend mounts `frontend/dist` at `/` only if it exists at startup.
